I totally see where you’re coming from—if /v1/products/id always returns the same output until it’s retired, it can feel stable. But the REST snag, as I understand it from Fielding’s ideas, is that URIs are meant to be timeless identifiers for resources—not tied to a specific version of how that resource is represented. When we bake v1 or v2 into the URI, clients end up hardcoding those paths, and that tight coupling can bite us later—like when v1 gets deprecated and apps break silently (I touched on this in the "Silent Client Failures" part).

With headers, the URI /products/id stays the same, and the Accept header just negotiates how the resource is shown (e.g., v1 fields vs. v2 with extras like price). So the resource’s identity doesn’t shift—only its representation changes, which aligns more with REST’s flexibility. I get your concern, though—if the behavior changes too much (not just presentation), it can feel like the header’s sneaking in a bigger shift than advertised. That’s a grey area for sure!
