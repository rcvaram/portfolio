Hi! Thanks for the thoughtful question—it’s a great point! You’re absolutely right that adding a new field to a JSON response is usually non-breaking, so it doesn’t always need a new version. Most folks only bump the version when there’s a bigger change, like new logic or a breaking shift.

In my header-based approach, the controller can handle this nicely. Yes, you can put different logic for each version in the same method, but keep it clean with some organization. For example, in my GitHub demo, the getProducts method uses a VersionProvider to figure out the version from the Accept header. Then, I pass that version to a service layer (IProductService) to handle the logic. It might look like this:

@GetMapping(value = "/products", produces = {"application/vnd.rcvaram.v1+json", "application/vnd.rcvaram.v2+json"})

public ResponseEntity<List<IProductResponseDto>> getProducts(@RequestHeader("Accept") String acceptHeader) {

Version version = versionProvider.identifyVersion(acceptHeader);

List<IProductResponseDto> products = productService.getProducts(version);

return ResponseEntity.ok(products);

}

Inside productService.getProducts(version), you could have a simple if or switch to branch the logic:

if (version == Version.V1) {

// V1 logic: simpler response, maybe no price field

return productRepository.findAll().stream().map(Product::toV1Dto).toList();

} else {

// V2 logic: add price or extra fields

return productRepository.findAll().stream().map(Product::toV2Dto).toList();

}

This keeps everything in one controller, avoiding duplication, while letting the service layer handle version-specific details. Does that make sense for your use case? I’d love to hear how you handle logic differences now!
