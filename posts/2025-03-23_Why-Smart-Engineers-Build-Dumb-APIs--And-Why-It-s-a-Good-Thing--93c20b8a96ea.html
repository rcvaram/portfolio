Why Smart Engineers Build Dumb APIs (And Why It’s a Good Thing)

Over-Engineering kills your APIs

Early in my career, I thought I was smart.

I wanted to build APIs that never break. I tried to make them future-proof.

I thought,

“If I plan for every future change now, I won’t need to update my API later.”
I was wrong ❌❌❌❌❌❌❌❌❌

Future-Proofing Sounds Smart, But It’s a Trap

Think today, we need to save a user’s phone. A simple API UserDto would look like this:

public class UserDTO {
    private String phone;
}
✅ Works today.
✅ Easy to understand.
✅ No confusion.

Ohh Nope, Let me rethink.

But I thought,

“What if users can have multiple phones in the future?”

So, I designed this instead:

public class UserDTO {
    private List<String> phones;
}

✅ Supports single and multiple phone numbers to take.
 ❌ Clients get confused — should they send an array or a string?
 ❌ Backend logic gets more complex for no reason.

I created a problem that didn’t exist — OverEngineering

RealOverThinker Engineer: Random Attributes

When an overthinker joins as a REST API developer. He feels like below

“New fields might come later. Let’s allow clients to send anything!”

He designed the Dto below,

public class UserDTO {
    private String phone;
    private Map<String, Object> customAttributes;
}

He expected clients can send anything like the below

{
    "phone": "+123456789",
    "customAttributes": {
        "workNumber": "+987654321",
        "isWhatsApp": true,
        "preferredContactTime": "evening"
    }
}

is it Flexible? Never, a nightmare for either party.

❌ No control over what clients send.
❌ Clients doubt their self what they can send.
❌ No validation.
❌ No clear API contract.
❌ More complex Backend logic.

But What About APIs That Need to Evolve?

Over-engineering is bad, but ignoring real future needs is equally dangerous.

Breaking changes are painful when building a public API with thousands of integrations A little anticipation helps, but wild guessing doesn’t.

✅ Plan for respectable Growth of your API

Think about what will change soon actually.

  • Payment methods evolving (e.g., adding more payment options as they become popular).
  • Authentication flows changing (e.g., integrating new security standards like MFA).

These are expected, so design with them in mind.

❌ Don’t Predict Every Change

Avoid trying to plan for every potential change that might never happen.

  • Adding random fields customAttributes just in case a use case comes up.
  • Introducing features extraData without clear requirements or user demand.
Focus on real needs, not wild guesses.

How to Build Better APIs

instead of guessing the future, follow these rules:

  1. Use API versioning for breaking changes.
  2. Use optional fields instead of big changes
  3. Solve Problems when they happen

1. Use API Versioning for Breaking Changes

When requirements change from the client, introduce a new version. There are several types of versioning. You can choose the one that suits you and your client best. Make them happy rather than focusing solely on making the engineers happy.

public class UserDTOv2 {
    private List<String> phones;
}
  • v1: Accepts phone: string
  • v2: Accepts phones: array

2. Use Optional Fields Instead of Big Changes

If new data is needed, add optional fields.

public class UserDTO {
    private String phone;
    private String alternatePhone; // Optional for future use
}

Old clients keep using phone. New clients can use alternatePhone.

3. Solve Problems When They Happen

  • If a new feature is needed, add it when required.
  • If clients request a change, update the API safely.
  • Don’t guess the future. YAGNI (You Ain’t Gonna Need It).

Final Thoughts: Keep It Simple!

Future-proofing sounds smart. It’s not.

  • Keep APIs clear and easy to use.
  • Don’t overcomplicate things before you need to.
  • Evolve APIs step by step, when needed.
A great API is predictable, simple, and easy to maintain. Don’t make your clients suffer.
