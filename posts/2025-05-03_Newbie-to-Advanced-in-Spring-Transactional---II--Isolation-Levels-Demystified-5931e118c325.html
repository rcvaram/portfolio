Introduction to Isolation Levels

Single line Def: Isolation defines how and when changes made by one transaction become visible to other concurrent transactions.

Spring doesn’t enforce isolation levels — it delegates that responsibility to the underlying database via JDBC.

The database must support the requested isolation level; otherwise, the closest supported level is applied (or an error may occur, depending on the driver).

The database (not Spring) enforces the rules — managing row locks, creating MVCC snapshots, or blocking other writes.

Data Anomalies in Concurrent Transactions

Let’s first understand the types of problems we want to avoid.

1. Dirty Read — Reading Uncommitted Data

You read something that the other transaction hasn’t committed yet. If that transaction rolls back, your read was dirty (never real)

RealWorld Ex: You see John’s balance as $4000, but the transaction gets rolled back. It's Fake news.

2. Non-Repeatable Read — Data Changes Mid-Transaction

You read the same row twice inside your transaction and get different results because another transaction committed a change in between.

RealWorld Ex: You check a row twice in your transaction, and it changes mid-way.

3. Phantom Read — New Rows Appear

New rows appear when you run the same query twice

RealWorld Ex: You SELECT rows, someone inserts more matching rows, and they come up in the second read.

Real-World Analogy: John, Adam, and a Banking App

Let’s ground this with a banking scenario:

  • T1: John transfers $1000 to Adam
  • T2: The Manager checks Adam’s account balance

Depending on the isolation level, T2 might:

  • See Adam’s new balance
  • See the old balance
  • See something in between
  • Or… wait for T1 to complete

That’s isolation in action.

1. 🔐— READ_UNCOMMITTED

  • Allows: Dirty reads
  • Use Case: Rarely. Danger zone.

Scenario:

T1 (Transfer): READ_UNCOMMITTED T2 (Admin Check): READ_UNCOMMITTED

  1. John's Account Balance is $40000.
  2. T1 debits $1000 from John but hasn’t committed.
  3. T2 Manager reads John’s balance → $3000.
  4. T1 rolls back later.

🧨 T2 has seen invalid data (dirty read).

📌You’re reading someone’s draft. Dangerous in financial apps.

2. 🔐 — Read_Committed [Most Common Default]

  • Prevents: Dirty reads
  • Allows: Non-repeatable reads, phantom reads

This is the default in PostgreSQL and Oracle. Behind the scenes: Your DB checks the visibility of each row version at query time. If not committed, it hides it.

Scenario:

T1 (Transfer): READ_COMMITTED T2 (Admin Check): READ_COMMITTED

  1. T1 debits John and commits
  2. T2 reads: $3000
  3. Another credit comes in
  4. T2 reads again: $4000
✅ No dirty read But ❌ non-repeatable read occurs → Same query, different results.

📌 This is usually safe for most OLTP apps.

3. ♻️ Repeatable Read

  • Prevents: Dirty reads, non-repeatable reads
  • Allows: Phantom reads

Behind the scenes, the database provides a consistent snapshot of the data as it existed when the transaction began. 📦 It’s like putting your reads in a time capsule.

Scenario:

T1 (Transfer): READ_COMMITTED (or higher) T2 (Report Generation): REPEATABLE_READ

  1. T2 (reporting) starts and reads John’s balance: $4000
  2. T1 updates and commits: new balance $3000
  3. T2 re-reads: still sees $4000
✅ Consistent reads ❌ But a second SELECT with WHERE amount > 1000 may return new rows inserted during T2

📌 In PostgreSQL, REPEATABLE_READ uses MVCC and does NOT prevent phantom reads.

4. 🛡️ Serializable

  • Prevents: Dirty reads, non-repeatable reads, phantom reads
  • Behaviour: Fully isolated transactions

🧱 Feels like single-threaded DB usage. Safe, but expensive.

Scenario:

T1 (Transfer): SERIALIZABLE T2 (Report): SERIALIZABLE

  1. T1 and T2 are both SERIALIZABLE
  2. If they overlap and conflict, one gets rolled back
✅ Full isolation ❌ May result in retry logic or decreased throughput

📌 In Postgresql, SERIALIZABLE uses Serializable Snapshot Isolation (SSI): concurrent transactions proceed, but conflicting ones fail at commit.

What’s Spring’s Default Isolation Level?

Simply, Spring passes this to your DB, so the DB’s default takes over.

  • Postgres, Oracle → READ_COMMITTED
  • Mysql (Innodb) → REPEATABLE_READ
⚠️ Not all databases support all isolation levels. Some will silently downgrade your request.

✅ Best Practices

  • READ_COMMITTEDsuitable for most online transaction systems (safe + performant)
  • REPEATABLE_READUse for consistent read snapshots (e.g., reporting)
  • SERIALIZABLE Only use if strict consistency is a must, and you’re prepared for retries
