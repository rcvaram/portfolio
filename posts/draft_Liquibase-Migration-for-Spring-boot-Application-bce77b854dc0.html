Liquibase Migration for Spring boot Application


Liquibase provides an automated version based database migration for the application. Liquibase tracks changes using its own tables in the application schema to ensure consistency and to avoid corruption due to incorrectly altered changelogs. It records a hash of each changeset. While it’s running updates, it puts a “lock” on the database so no one can accidentally run two changelogs concurrently.

Liquibase Concepts

Changeset

A changeSet describes a set of database changes that Liquibase executes within one transaction. Each changeSet gets identified by the name of the author and an id.

Liquibase stores this information together with the name of the changelog file in the databasechangelog table to keep track of the executed changesets. A changeset can be applied to the database only once.

When a changeset is included then the liquibase looks at the databasechangelog table to verify the changelog is already executed or not. If the changelog is already executed in that database, it will skip that changelog otherwise it will run the changelog. Changelogs can be written in JSON, YAML, XML or SQL. It is best practice to have just one change per changeset unless there is a group of non-auto-committing changes that you want to apply as a transaction such as inserting data.

Changelog file

All the changes are defined as changesets and they will be added in the changelog file. then the liquibase run those changesets sequentially. When the Liquibase migrator runs, it parses the changelog tag. The migrator first checks any preconditions specified. If any of the preconditions fail, Liquibase will exit with an error message explaining what failed. Preconditions can be typically used for both documenting and enforcing expectations or assumptions. For example, you can specify the DBMS to be run against the changelog or the user you should log in to run changes.

Liquibase context

Contexts in Liquibase are expressions that can be added to changesets/changelog to control which will be executed in any particular migration run. Any string can be used for the context name and they are checked case-insensitively. If ya context is not set for a changeset, it will run all the time, regardless of what contexts are passed into the migrator.

Generating changelog file for an already existing database

with the help of dbeaver database tool, We can generate the database schema & static data in SQL format. Since the changelog can be defined in SQL format, there are no big changes in the generated files. We have to do some minor changes such as removing the database schema name in the SQL format file.

We can use the liquibase command-line tool to generate the changelog but, triggers are not available in the community edition because of that, we don’t have trigger changesets in that generated changelog file.

Liquibase Configurations for the Application

Gradle liquibase dependency

Add liquibase dependency in your spring boot application build.gradle file to work with liquibase

compile 'org.liquibase:liquibase-core:4.3.3'

Changelog file configuration

Since the API is a spring boot application, liquibase bean definition is not needed. Liquibase needs to know the changelog file path to run the changes in the database. For that, the Liquibase path needs to be configured in the application.properties file as follow.

liquibase.change-log=classpath:liquibase-changeLog.xml

Common Best practice is, adding a parent changelog file named master-changelog.xml and adding changelog files in there.

The default changelog file path is src/main/resources/db/changelog/db.changelog-master.yaml. If the master changelog is defined in the default path then, there is no need to configure the liquibase change log path.

Inside this db.changelog-path.master.yaml, we only include changelog files, not changesets.

databaseChangeLog:
  - include:
      file: db/changelog/ncob_schema.sql
      context: dev,prod,qa

Using liquibase context to run the changelog file for the specific environments

Lquibase changelogs can be run based on the context. For example, We don’t need to run the particular changelog in the dev environment but we need to run that in prod and qa environments. For that scenario, what we have to do is, When we include the particular changelog file in the master changelog file we need to mention the context. then in the application properties, we have to configure the context of liquibase.

In the master changelog file

databaseChangeLog:
  - include:
      file: db/changelog/ncob_schema.sql
      context: prod,qa

In application.properties file

spring.liquibase.contexts=dev

When the context is configured as dev then the particular changelog will not be run and it is skipped by the liquibase.

If we change the context to prod database changes on that changelog will be run.

in application.properties file

spring.liquibase.contexts=qa

Liquibase configuration enable/disable option

Liquibase migration’s execution on startup can be enabled/disabled by configuring the spring.liquibase.enabled property. This way, all the remaining Liquibase configuration stays untouched.

spring.liquibase.enabled=false
