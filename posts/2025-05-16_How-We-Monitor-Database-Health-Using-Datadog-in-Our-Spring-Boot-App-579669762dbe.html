How We Monitor Database Health Using Datadog in Our Spring Boot App

If your app needs better DB monitoring, this guide shows how we fixed that gap using custom metrics and Datadog.

We have a simple Spring Boot application. It consumes messages from SQS, saves them in the PostgreSQL database, and then sends them to Kafka.

Since our app depends on external systems: SQS, PostgreSQL database, and Kafka, we need a way to handle failures, especially if one of these systems goes down.

One of the most important failures we want to alert our team to is when the database goes down.

We use Datadog for logging, monitoring, and alerts.

Some of these, like jdbc.connections.active, show how many database connections are being used. But they don’t tell us if the database is healthy, especially when the app isn’t getting much traffic.

So we built our own metric and pushed it to Datadog ourselves.

Step 1: Add Required Dependencies

Step 2: Configure Application Properties

We added the following properties in the application.properties file

💡 Note: We keep some values (like API keys or environment tags) in environment variables because they change depending on the environment

1. management.datadog.metrics.export.api-key — Datadog API key. Use an environment variable like ${DATADOG_API_KEY} for security.

2. management.datadog.metrics.export.enabled — Turns on sending metrics to Datadog. For some environments, you can turn off so it will reduce the cost from datadog.

3. management.datadog.metrics.export.step — If you set this to 30 seconds, Metrics are sent to Datadog every 30 seconds.

4. management.metrics.tags.env , management.metrics.tags.service , management.metrics.tags.team — These are tags; these will be used to easily group and identify the metric in Datadog.

Step 4: Create a Custom Metric

Turn the DB health status into a gauge metric.


import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.actuate.health.HealthComponent;
import org.springframework.boot.actuate.health.HealthEndpoint;
import org.springframework.boot.actuate.health.Status;
import org.springframework.stereotype.Component;

@Component
public class DataSourceHealthGauge {

    private final HealthEndpoint healthEndpoint;

    @Autowired
    public DataSourceHealthGauge(MeterRegistry meterRegistry, HealthEndpoint healthEndpoint) {
        this.healthEndpoint = healthEndpoint;
        Gauge.builder("custom.health.db.status", this::getHealthStatus)
                .description("Database health check status: 1 = UP, 0 = DOWN")
                .register(meterRegistry);
    }

    private double getHealthStatus() {
        HealthComponent dbHealth = healthEndpoint.healthForPath("db");
        return dbHealth.getStatus().equals(Status.UP) ? 1.0 : 0.0;
    }
}

We use Spring Boot’s built-in health check system (HealthEndpoint) to get the status of the database.

Then we use Micrometer's Gauge to define a metric called custom.health.db.status.

This metric returns 1.0 when the database is UP and 0.0 when it's DOWN.

Datadog will now receive the metric custom.health.db.status every 30 seconds.

So,

With this custom metric, we tell

Hey Micrometer, here’s a new metric called custom.health.db.status. Every time you send it, run this method (getHealthStatus()) and report 1 if the DB is up, or 0 if it's down.

Building this custom metric gave us precise visibility into a critical dependency — our PostgresSQL database.

It’s always better to track the real heartbeat than to chase signals that don’t tell the full story. Instead of relying on noisy or indirect metrics, we now get alerted exactly when it matters.
