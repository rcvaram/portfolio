App Functionality — Simple

We’ve built a Spring Boot 2 application running on Java 17 and deployed as a service in AWS ECS.

Every 30 minutes, our Spring Boot app asked to do a job:

  1. It scans an SFTP folder for incoming files.
  2. Each file contains anywhere from 1,000 to 5,000 lines.
  3. A 10-thread pool processes each line in parallel.
  4. The processed data is sent to Kafka for downstream consumption.

It’s a batch-style workflow — high load for a few minutes, then idle. The job most of the time finishes in under 10 minutes, leaving the app idle for the next 20 minutes.

When we see this

Everything works perfectly in development until the App meets the performance testing.

During the performance test, something odd happens.

CPU looks fine around 40% always.

Memory ? — Hmm need to analyse

After every test cycle, memory usage spiked and never came back down. not after the first run, not after the second. By the third, Memory usage never came back down.

My QA engineers start asking: “Is this a memory leak? Will it keep growing? Are we going to run out of memory?”

I trusted the JVM. I trusted Java 17. But this was something deeper — a flaw in plain sight.

What I discovered about Java 17’s default GC, especially in containerised environments like ECS, was eye-opening, and it might just save you from the same headache.

Java 17 Default Garbage Collector Behaviour

Since we use the default garbage collector in Java 17, it uses G1GC

  1. Cleans the new objects area often (young objects).
  2. Puts older objects into the old generation if they’re still needed.
  3. Only cleans the old generation area when it’s nearly full.

👉 So what happens?

  • G1 keeps some old objects because it thinks we might want to use them again.
  • It doesn’t give space back to our EC2 instances easily, even when it has more than enough room.

That’s why our memory usage keeps growing — It’s not bad, but when we look, it's scary.

Don’t panic about memory usage with G1 — it’s expected.

But the Story doesn’t end here…

The Problem with G1GC in Containers

Our ECS setup had a soft memory reservation (memoryReservation = 1024m) but no hard memory limit (Xmx). 
So the JVM assumed it had access to all the memory on the host.

And G1GC? It thought:

“Why clean up now? I’ve got space. Maybe they’ll need this memory again soon.”

So:

  • G1 GC delays major cleanup
  • Memory keeps growing (because it thinks more memory = better performance)
  • GC waits until memory is almost full to do a big cleanup (which may come too late)

This is exactly what we saw:

Memory usage continues to grow in ECS, and G1GC doesn’t clear aggressively.

This wasn’t a memory leak. It was just… the GC doing its job badly, for our case.

And in a shared ECS environment, this behaviour is dangerous.

Our app could get killed, rescheduled, or just make poor neighbours for other containers.

The Fix That Wasn’t Enough

To Fix this issue, we may setup the -Xmx parameter for G1GC to tell JVM this is your memory limit.

Then G1GC knows okay this is my memory before reaching out that it can clean up and free the memory.

However still,

G1GC waits for memory pressure — it starts serious cleanup only when the heap gets full.

Even with a perfectly set -Xmx, G1GC has a weakness: It doesn’t return memory to the OS unless forced or manually tuned.

So, ECS thinks the container is “always using 1.5–2 GB” even after the app is idle.

So, we need a better solution

ZGC — The Active Cleaner

How ZGC Works:

  • It cleans all generations concurrently.
  • It frees memory asap after objects are no longer used.
  • It returns memory to the OS in real time.
  • It’s quiet, background-cleaning magic — with one cost: higher CPU.

But in our use case, that’s a trade we were happy to make.

Why We’ll Stick with ZGC

In our app’s lifecycle, every 30 minutes, it processes files for only 10 minutes — and then remains idle for the next 20. That idle period was our hidden bottleneck. Even with configured settings, G1GC kept memory allocated, assuming:

“You’ll probably need this memory again soon.”

But in our case, that assumption was wrong. We didn’t need the memory again — not for another 30 minutes.

ZGC changed everything. ZGC is built for burst-style, elastic workloads like ours. It releases memory when we don’t need it — and reclaims it quickly when we do.

With ZGC, our ECS containers are now:

✅ More memory-efficient
✅ Less risky in shared environments
✅ Able to scale and coexist cleanly with other ECS services

If you’re running Java in the cloud, especially with intermittent workloads or shared environments, don’t wait for a memory usage to scare you.

Switch to ZGC, and let your containers breathe again.
