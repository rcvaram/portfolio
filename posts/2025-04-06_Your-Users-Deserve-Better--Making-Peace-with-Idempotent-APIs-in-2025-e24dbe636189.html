What’s Idempotency?

Simply — No matter how many times you ask, the action only happens ONCE.

Imagine… you tap a “Pay Now” button 5 times because the app feels slow.
If the API is idempotent → it processes only one payment. The other 4? Ignored. Or the same response returned.

That’s it. That’s what Idempotency means.

Idempotency — User can do the same thing multiple times, but it only affects your system once.

Why Do These Bugs Happen?

Because the internet is messy — Life is messy.

  • The network drops
  • The app times out
  • The user hits refresh
  • Someone double-taps the button in panic

And if your backend can’t tell if this is a repeat, 
it just… does the thing again.

That’s how:

  • Users get charged twice
  • Two burgers get ordered
  • Same ticket gets booked twice

Scary, right?

You might have already built some APIs as Idempotent

You might already be doing it without knowing!

Examples:

  • GET /user/123 → Just reads data. Safe.
  • PUT /user/123 with same data → Just updates once.
  • POST /signup → Checks if the email exists and skips if it does.

These are naturally idempotent. No duplicate action happens even if retried.

These APIs are fine, so how can we make an API explicitly idempotent?

How to Make Your API Idempotent Explicitly?

Use something called an Idempotency Key.

The actual code

public class PaymentService {

    public PaymentResponse processPaymentRequest(HttpServletRequest request) throws InvalidRequestException {
        return processActualPayment();//Think like messy code...
    }

}

Let’s say your client sends a payment request:

POST /payment  
Idempotency-Key: abc-123

Now, your server should:

  1. Check if this key has been seen before.
  2. If yes → return the same old result.
  3. If no → process the request, save the key + response.
public class PaymentService {

    public PaymentResponse processPaymentRequest(HttpServletRequest request) throws InvalidRequestException {
        String idKey = request.getHeader("Idempotency-Key");

        //Check if the Idempotency-Key is missing or empty
        if (idKey == null || idKey.trim().isEmpty()) {
            throw new InvalidRequestException("Idempotency-Key is not present");
        }

        idKey = idKey.trim();

        PaymentResponse result = dataStore.get(idKey);

        if (result != null) {
            return result;
        } else {

            PaymentResponse processedResult = processActualPayment();
            dataStore.put(idKey, processedResult);
            return processedResult;
        }
    }
}

So even if the client retries…

👉 You don’t charge again.
👉 You just return the same success.

Boom. Problem solved. 💪

But Where Do We Store These Keys?

You’ve got options:

  • Database Table — Super reliable
  • Redis — Fast and great for short-term storage (like 24 hours)
  • In-Memory? ❌ Nope. Don’t do it Dear. It resets when the server restarts.

Other Ways to Prevent Duplicate Actions

Sometimes, you don’t need idempotency keys.

Natural Uniqueness (Email, Phone…)

Instead of passing a key, check if the user already exists:

POST /users { “email”: “me@example.com” }

If the email is already there → return that user.

  • ✅ Simple
  • ❌ Not a solution for payments or repeated actions

Database Constraints (Your DB Saves You!)

Use a unique column to block duplicates.

CREATE UNIQUE INDEX ON orders(order_reference_id)

Now, even if two requests fly in together, the DB allows only one.

  • ✅ Fast & safe
  • ❌ You’ll need to handle DB errors smartly

Use PUT Instead of POST (When You Know the ID)

PUT is idempotent by design.

PUT /users/123
{ "name": "Siva" }

Calling this again and again? Still one update.

  • ✅ Clean
  • ❌ Not for random POST stuff like payments or order creation
