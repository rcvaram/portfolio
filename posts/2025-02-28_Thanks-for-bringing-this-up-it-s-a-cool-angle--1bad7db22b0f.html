Thanks for bringing this up—it’s a cool angle! You’re suggesting something like v1.api.example.com/products and v2.api.example.com/products, right? That’s definitely a valid way to version APIs, and it keeps the resource path (/products) stable, which aligns with REST’s timeless URI idea.

It’s a bit different from my header-based approach, but it has its benefits—like separating versions at the infrastructure level (e.g., different servers or containers). Some big systems do this, like how Netflix might route traffic through different subdomains. The downside is you’d need DNS or load balancer setup for each version, which adds some ops overhead compared to headers, where it’s all in one endpoint.

In my demo, I went with headers (Accept: application/vnd.rcvaram.v1+json) to keep the URI /products forever and let the server handle versioning internally. But your host-based idea could work great, especially for isolated deployments! Have you seen this in action somewhere? I’d love to hear more!
