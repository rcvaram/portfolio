Recently, I got the requirement to update my API to a new version, also the old version running to support existing clients.

My original endpoint was /products.

So, I thought:

Let's switch to /v1/products the current version and /v2/products the new one. Simple, right?

GET /v1/products
GET /v2/products
This approach feels “yeah thats the way”,
BUT
It violates REST principles and creates maintaince hell.

Simpilicity Trap

@RestController  
@RequestMapping("/v1/products")  
public class ProductControllerV1 { ... }  

@RestController  
@RequestMapping("/v2/products")  
public class ProductControllerV2 { ... }

Yeah, it's Quick to implement right? Hmm… but, we have two controllers (and tests, docs…) to maintain.

Tutorials and legacy systems normalize URL versioning. If we check for versioning in Google, URL API versioning will be there from many sources.

Why Versioning in URLs Breaks REST?

URIs Should Be Timeless

REST mentioned that URIs are stable identifiers for resources. When we version URLs:

  • Clients hardcode paths like /v1/products, creating tight coupling.
  • Changing a URI is like changing a book’s ISBN — it breaks every library that references it.

It is not easy for Maintenance

After a few years,

/v1/products
/v2/products
/v3/products
/legacy/products

Now we’re stuck with:

  • Duplicate code.
  • Deprecated versions we can’t retire (clients still use them).
  • Bloated documentation.

Silent Client Failures

When /v1/productsis deprecated:

  • Mobile apps using it start returning 404s.
  • Users get no warnings — just broken functionality.

The RESTful Alternatives for API Versioning

Version via Headers

Use the Accept header to negotiate versions:

For V1 API

curl --location 'http://localhost:8080/products' \
--header 'accept: application/vnd.rcvaram.v1+json'

For V2 API

curl --location 'http://localhost:8080/products' \
--header 'accept: application/vnd.rcvaram.v2+json'

Java Code

Spoiler Alert: Full code can be found here: medium-api-versioning github
@RestController
@RequiredArgsConstructor
public class ProductController {
    private final VersionProvider versionProvider;
    private final IProductService productService;

   
    @GetMapping(value = "/products", produces = {
            "application/vnd.rcvaram.v1+json",
            "application/vnd.rcvaram.v2+json"
    })
    public ResponseEntity<List<IProductResponseDto>> getProducts(@Parameter(
            name = "Accept",
            description = "Specifies the response format and version. Defaults to v1 (application/vnd.rcvaram.v1+json) if omitted.",
            required = false ) @RequestHeader(value = "Accept", defaultValue = "application/vnd.rcvaram.v1+json") String acceptHeader) {
        Version version = versionProvider.identifyVersion(acceptHeader);
        List<IProductResponseDto> products = productService.getProducts(version);
        return ResponseEntity.ok(products);
    }
}

Pros

  • URIs remain stable (/products forever)
  • Backward compatibility is easier (serve multiple versions from one endpoint).
  • Caching works naturally (the version is part of the request headers).

Cons

  • Clients must configure headers (some tools/libraries make this non-trivial)
Stripe: Scaled to 10+ API versions without URL clutter by using headers.

Versioning via Custom Media Types

Why It Works

Media types (like application/vnd.github.v3+json) explicitly declare the format and version, decoupling versioning from URIs.

How to Implement

Define media types for each version:

GET /users HTTP/1.1  
Accept: accept: application/vnd.rcvaram.v2+json

Server-Side Logic:

  • Parse the Accept header to determine the version.
  • Return data in the requested format.

Real-World Examples:

  • GitHub: Accept: application/vnd.github.v3+json
  • Stripe: Accept: application/vnd.stripe.v2+json

Pros:

  • A clear, standardized way to negotiate versions.
  • Supports semantic versioning in media types (e.g., v1.2.3)

Cons:

  • Requires documentation to educate clients
GitHub: Maintained backward compatibility for years via media types.

Why These Alternatives Are Better Than URL Versioning

  1. Stable URIs: Clients bookmark /products, not /v1/prodcuts.
  2. Backward Compatibility: Serve old and new versions from the same endpoint.
  3. Cleaner Code: No duplicate controllers or routes.
  4. REST Compliance: Aligns with Fielding’s constraints.

If you can’t get rid of URL Versioning Then It Should be,

Only in two cases:

  1. Internal APIs (microservices you control).
  2. Breaking Changes That Alter Resource Identity (GDPR-mandated structural shifts).
Even then, ask: “Can we version via headers instead?”

Key Takeaways

  1. URIs are forever — don’t tightly coupled them to versions.
  2. Headers > URLs for scalability and REST compliance.
  3. Educate clients to use Accept headers—it’s worth

From other developers — (Thanks to Readers!)

Q1. Does URL Versioning Really Break REST? (Credit: Bill Miller)?

Ans: Fielding says URIs should be timeless, and versions in URLs tie resources to specific formats, which clients shouldn’t need to know upfront Ref: Fielding’s Untangled Blog. Bill also runs separate services (e.g., v1 in one container, v2 in another) — that’s a smart way to isolate versions, though headers can do this too with load balancing.

Q2.How Do Headers Work with Swagger? (Credit: Lars Schirrmeister )

Ans: My GitHub demo (Spring Boot API Versioning) shows it: one endpoint with produces listing both versions. Swagger can show different responses based on the Accept header — check out Versioning REST API with Swagger for setup tips.

Q3: Why Is URL Versioning So Common? (Credit: Robin Schmid)

Ans: Robin asked why URL versioning is everywhere if headers are better. Simple: it’s quick, easy to see in logs, and feels familiar. But as Chris Hornberger said, it’s often “legacy thinking” or laziness. Headers take more effort but scale better — GitHub and Stripe prove it. Robin’s right that my if/else code isn’t perfect, but it’s still less messy than tons of controllers.

Q4: What About Hardcoding Headers? (Credit: Andreas Vent-Schmidt)?

Ans: Andres pointed out clients can hardcode headers too. True! That’s why we must tell clients about new versions — headers don’t fix that alone. Chris suggested making headers mandatory or defaulting to v1, so old clients still work while new ones get v2 features.

Q5: Query Params vs. Headers? (Credit: octree)

Ans: Octree asked why not use query params (e.g., /products?version=1). It’s simple and logs well, but headers are made for negotiation in REST, keeping URIs cleaner. Headers are growing popular — GitHub and Stripe lead the way.

Q6: Deprecation Matters (Credit: Stanley Masinde)

Ans: Stanley shared a workflow where old versions die fast using OpenAPI deprecation tags. That keeps URL versioning manageable. Headers can help here too — warn clients with headers like X-DEPRECATION-WARN and phase out old formats Ref: API Deprecation Strategies.

Q7: Endpoint Dependencies (Credit: Nick Maiorano)

Nick made a killer point: what if one endpoint stays v1 but another tied to it goes v2? URL versioning forces duplication or mixing versions, breaking consistency. Headers avoid this, keeping APIs smooth and scalable.

Q8: Team Resistance (Credit: Jay Simonini)

Jay fights the same battle — teams love URL versioning because “it’s always been that way.” Demos like mine and big-name examples can sway them.
