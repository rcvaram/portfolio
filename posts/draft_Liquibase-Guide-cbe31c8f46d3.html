Liquibase Guide

Liquibase provides an automated version based database migration for the application. Liquibase tracks changes using its own tables in the application schema to ensure consistency and to avoid corruption due to incorrectly altered changelogs. It records a hash of each changeset.

 While it’s running updates, it puts a “lock” on the database so no one can accidentally run two changelogs concurrently.

Before going into liquibase, we need to understand the basic concepts of liquibase.

Liquibase Concepts

Changeset

A changeSet describes a set of database changes that Liquibase executes within one transaction. Each changeSet gets identified by the name of the author and an id.

Liquibase stores this information together with the name of the changelog file in the databasechangelog table to keep track of the executed changesets. 

When a changeset is included then the liquibase looks at the databasechangelog table to verify the changelog is already executed or not. The default behaviour of liquibase is, If the changelog is already executed in that database, it will skip that changelog otherwise it will run the changelog. Changelogs can be written in JSON, YAML, XML or SQL. 

It is best practice to have just one change per changeset unless there is a group of non-auto-committing changes that you want to apply as a transaction such as inserting data.

Changelog file

All the changes are defined as changesets and they will be added in the changelog file. then the liquibase run those changesets sequentially. When the Liquibase migrator runs, it parses the changelog tag. The migrator first checks any preconditions specified. If any of the preconditions fail, Liquibase will exit with an error message explaining what failed. Preconditions can be typically used for both documenting and enforcing expectations or assumptions. For example, you can specify the DBMS to be run against the changelog or the user you should log in to run changes.

Liquibase context

Contexts in Liquibase are expressions that can be added to changesets/changelog to control which will be executed in any particular migration run. Any string can be used for the context name and they are checked case-insensitively. If ya context is not set for a changeset, it will run all the time, regardless of what contexts are passed into the migrator.
