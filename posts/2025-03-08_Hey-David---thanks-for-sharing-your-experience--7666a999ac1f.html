From My POV: This is what I do

1. Default Version Handling

Since your system defaults to V1 and that decision is now locked in,

YOu can introduce a warning mechanism. You could log missing version headers and return a response header like:

X-API-Warning: "No version specified, defaulting to v1. Please use Accept header."

This make clients toward explicit versioning while still being backward-compatible.

2. Logging Headers

You're right—many logging solutions focus on URLs, and headers often require extra setup.

WA 1: If using an API gateway (AWS API Gateway), you can configure it to extract and log the Accept header automatically.

WA2: In Spring Boot, adding a filter to log version headers before processing requests.

incase, team finds that URI versioning significantly reduces friction, it's fair to prioritize practicality over REST purism

Headers work well when tooling and client education are strong. But if they’re adding more pain than value in your case, a hybrid approach (e.g, supporting both for a transition period) could be a possilbe work around.
