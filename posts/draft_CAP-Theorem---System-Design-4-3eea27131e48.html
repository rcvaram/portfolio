CAP Theorem — System Design 4

What Partition Tolerance Means:

Partition tolerance means that even when some parts of the system (like your friends) are disconnected, the rest of the system keeps running.

  • The system doesn’t completely crash.
  • It continues to serve the users who are still connected.

Examples to Understand This:

Example 1: A Chat App

  • Without Partition Tolerance: If there’s a network issue, the entire chat app crashes for everyone. Nobody can send or receive messages.
  • With Partition Tolerance:
  • Users who can still connect to the servers can keep chatting.
  • The disconnected users will get their messages later, once the network is fixed.

Example 2: Online Shopping

  • Imagine Amazon’s website faces a network issue that cuts off one of its data centers.
  • Without Partition Tolerance: The entire site would go down for all users.
  • With Partition Tolerance: The rest of the data centers continue working, and most users can keep shopping.

Why Is Partition Tolerance Important?

In distributed systems (like online games, chat apps, or shopping platforms):

  • Network problems are inevitable.
  • A system that can’t handle partitions would completely stop working whenever something goes wrong.

Partition tolerance ensures the system can handle these issues and keep running for as many users as possible.

Key Idea: The System Never Crashes Completely

Partition tolerance doesn’t mean the system works perfectly during a partition, but it ensures:

  1. Some parts still work (like connected users).
  2. It recovers gracefully when the network problem is fixed.

Amazon Aurora Cluster and Partition Tolerance

Amazon Aurora is a distributed relational database designed for high availability and fault tolerance. Let’s explore how it handles partition tolerance:

Scenario: Network Partition in an Aurora Cluster

Imagine an Aurora cluster with:

  • One primary node (writer).
  • Multiple replicas (readers) across Availability Zones (AZs).

A network partition isolates one or more replicas from the primary node.

How Aurora Maintains Partition Tolerance

  • Consistency Focus (CP System):
  • The primary node continues to handle write requests, even if some replicas are partitioned.
  • The partitioned replicas become inaccessible for updates until they can resynchronize with the primary node.
  • Aurora ensures strong consistency by only accepting writes to the primary node.

  • Availability for Reads:
  • Partitioned replicas can continue serving read-only requests for eventual consistency.
  • Once the partition is resolved, replicas sync with the primary node to regain up-to-date data.


Key Design Elements in Aurora for Partition Tolerance

  • Distributed Storage Engine: Storage is split across multiple AZs and is fault-tolerant to AZ failures.
  • Quorum-Based Writes: Aurora writes data to a majority of storage nodes before confirming the write, ensuring consistency even during partitions.

Trade-offs in Aurora

  • Sacrifices Availability for Writes: During a partition, some write operations may fail to ensure consistency.
  • Maintains Partition Tolerance: The system doesn’t crash and continues to operate partially.

Apache Kafka and Partition Tolerance

Kafka is a distributed event-streaming platform designed to handle partitions and provide availability.

Scenario: Network Partition in Kafka

Imagine a Kafka cluster with:

  • Multiple brokers (nodes).
  • A leader broker for each topic partition.
  • Followers replicate the leader’s data.

A network partition isolates some brokers from the cluster.

How Kafka Maintains Partition Tolerance

  • Replication and Leadership:
  • Each partition has a leader broker and several replica brokers.
  • If the leader broker becomes unreachable due to a network partition, Kafka elects a new leader from the replicas that are still connected to the majority of the cluster.

Availability Focus (AP System):

  • Kafka prioritizes availability and continues to accept writes and reads as long as the leader for a partition is available.
  • Some writes might be lost or delayed until partitioned nodes rejoin the cluster.

Consistency through Acknowledgment:

  • Kafka provides tunable consistency:
  • acks=all ensures writes are replicated to all in-sync replicas before acknowledgment.
  • acks=1 sacrifices consistency for availability by acknowledging writes after a single replica receives them.
