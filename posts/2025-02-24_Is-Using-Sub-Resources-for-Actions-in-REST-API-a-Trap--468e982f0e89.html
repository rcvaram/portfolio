What Sub-Resources for Actions?

At its core, RESTful APIs focus on resources — nouns like orders, users, and products.

But what about actions? How should we handle things like cancelling an order or activating a user account?

Here are the three common approaches:

1. Sub-resource approach: POST /orders/{orderId}/cancel
2. Query parameter approach: POST /orders/{orderId}?action=cancel 
3. Request body approach: POST /orders/{orderId} with { “action”: “cancel” } in the body

The sub-resource approach treats actions as their own entities, giving them dedicated endpoints.

The Case for Sub-Resources: When They Shine ✨

1. Clean and Predictable API Structure

A URL like POST /orders/{orderId}/cancel is easy to read and instantly tells developers what’s happening.

sub-resources make APIs more intuitive and self-documenting compared to the action in query parameters or request payloads.

This aligns with REST’s uniform interface constraint, which promotes simplicity and scalability by enforcing a consistent structure across resources.

2. Better Discoverability (HATEOAS Support)

REST APIs should ideally be discoverable, meaning clients should be able to navigate them without extensive documentation.

Sub-resources fit well with Hypermedia as the Engine of Application State (HATEOAS), allowing APIs to expose available actions as links. For example, /orders/{orderId} can return a link to/cancel, guiding clients naturally.

3. Improved Caching and Observability

Explicit URLs allow caching mechanisms and logging tools to track requests more effectively.

HTTP’s caching mechanisms rely on URLs and methods to store and retrieve responses efficiently. A dedicated POST /orders/{orderId}/cancel endpoint is easier for proxies and CDNs to handle than a generic POST /orders/{orderId}with varying payloads.

If you want to audit how often cancellations happen, it’s much easier with a dedicated endpoint.

4. Clearer Authorization Rules

With separate sub-resource endpoints, you can easily define permissions.

For example, restricting access to POST /orders/{orderId}/cancel is more straightforward than checking request payloads in a generic POST /orders/{orderId}endpoint.

This enables fine-grained access control, crucial for APIs with role-based permissions.

The Hidden Pitfalls of Sub-Resources 🚨

1. API Explosion: Too Many Endpoints

If every action gets a dedicated sub-resource,

your API quickly becomes unmanageable. Imagine an orders resource with actions like: 
 — POST /orders/{orderId}/cancel 
 — POST /orders/{orderId}/refund 
 — POST /orders/{orderId}/approve
 — POST /orders/{orderId}/archive

Now multiply this across multiple resources. Before you know it, your API is drowning in endpoints, making documentation, testing, and versioning a nightmare. This sprawl increases the API’s surface area, complicating maintenance.

2. Not Everything Fits the Resource Model

Some actions don’t neatly belong as sub-resources. Consider bulk operations: 
- 🚫 POST /orders/cancel-multiple/{orderIds} (awkward and unnatural) 
- ✅ POST /orders/batch-cancel with { “orderIds”: [123, 456] } (cleaner and more flexible)

Forcing actions into sub-resources can lead to unnatural designs that hurt long-term maintainability.

Bulk operations, asynchronous tasks, or actions that span multiple resources often resist the sub-resource treatment.

3. REST Purity vs. Practicality: The Verb Dilemma

REST advocates emphasize noun-based URLs, yet sub-resources often introduce verbs (/cancel, /approve).

While practical, this contradicts REST principles, sparking debates on whether sub-resources are actually RESTful or just a convenient hack.

REST purists argue for payloads or query parameters to keep URLs noun-focused, though real-world APIs often bend this rule for usability.

4. Harder to Evolve Over Time

What if your the POST /orders/{orderId}/cancel endpoint needs an additional reason parameter?

  • Do you modify the URL (/cancel/{reason})?
  • Add a query parameter (?reason=xyz)?

breaking the endpoint’s purity? Accept a request body, which POST already allows but feels inconsistent? Payload-based actions (POST /orders/{orderId} with { “action”: “cancel”, “reason”: “customer request” }) adapt more gracefully.

5. Tooling and Framework Limitations

Not all API frameworks handle deeply nested sub-resources well.

Some require extra routing configurations, while others struggle with auto-generating documentation.

For example, frameworks like Express.js or ASP.NET Core often require additional setup for nested routes, impacting development velocity.

If your framework doesn’t natively support sub-resources, you may be in for a painful experience.

When Should You Use Sub-Resources? ✅

Sub-resources are most effective when:

  1. The action represents a state transition ( cancelling, activating, refunding).
  2. It applies to a single resource instance (not bulk operations).
  3. Readability and discoverability are critical for your API consumers, especially for public APIs.

When to Avoid Them? ❌

  1. When handling bulk operations — use a request body for flexibility.
  2. If your API starts suffering from endpoint explosion — consider consolidating actions.
  3. If you anticipate frequent evolution — payload-based actions are more adaptable.

The Hybrid Approach: Best of Both Worlds 🌎

Who says you have to choose one or the other? Many APIs use a hybrid model:

  • Use sub-resources for simple, high-visibility actions: POST /orders/{orderId}/cancel for straightforward state transitions.
  • Use request payloads for complex, evolving operations: POST /orders/actions with { “action”: “cancel”, “orderId”: 123, “reason”: “Customer request” } for richer workflows.

This keeps your API intuitive while allowing flexibility where needed. Stripe’s API, for example, uses sub-resources for common actions /v1/charges/{chargeId}/capture while relying on payloads for more complex operations.

Context Is King 👑

Sub-resources can make REST APIs more readable and predictable, but they aren’t fit for all use cases.

Their effectiveness depends on the complexity of your domain, the scalability of your API, and the needs of your consumers.

Ask yourself:

  1. Does this action truly belong as a sub-resource, or am I forcing it?
  2. Will my API become harder to maintain with too many action endpoints?
  3. How flexible do I need this action to be in the future?

What’s your take? Have sub-resources made your API better, or have they caused more headaches than they solved?
