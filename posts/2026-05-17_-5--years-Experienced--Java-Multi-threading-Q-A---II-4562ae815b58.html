1. What is Java Memory Model?

First, it is a specification that defines how threads interact with shared memory and what visibility guarantees exist between them.

Thread may cache variables locally in CPU caches or registers for performance reasons. So there is a change when a thread updates a variable, another thread may not see the updated value unless synchronization mechanism, visibility guarantees are used.

The Java Memory Model provides the rules that guarantee:

  • Visibility → Whether the change of a particular thread in variable is visible for another threads or not
  • Ordering → JVM, compiler and CPU may reorder instructions for optimizations. In multithreaded systems, this can create unexpected behaviors if synchronization is missing.
  • Atomicity behavior

Java Memory Model (JMM) defines a concept called happens before relationship.

This happens before relationship concept guarantees memory visibility and ordering between operations.

Examples for happens before relationship

  • A write to a volatile variable happens-before every subsequent read of that variable.
  • Existing synchronized block happens-before another thread enters the same synchrnonized block.

Synchronization mechanism like:

  • Volatile
  • synchronized
  • Lock
  • Atomic classes
  • concurrent collections

all backbone is JMM.

 boolean running = true;

One thread may update the flag to false but another thread may continue seeing the old cached value and loop forever.

volatile boolean running = true;

once we add this keyword, it guarantees visibility of the latest value across threads.

2. Does happens before guarantee atomicity?

No. It guarantees visibility and ordering. It does not provide compound-operation safety.

3. What is ConcurrentHashMap?

ConcurrentHashMap is a thread safe implementation of Map designed for high concurrency.

Java HashMap is not thread-safe. When we do concurrent modifications can lead to

  • race conditions
  • inconsistent data

This HashMap concurrency issue is solved in Hashtable by synchronizing every method. Underneath, It has a single global lock. Since it has a single global lock, at a time only one thread can access the map which reduces the concurrency.

ConcurrentHashMap improves the concurrency by allowing multiple threads to read and update the map concurrently with much finer-grained synchronization.

ConcurrentMap<String, String> map = New ConcurrentHashMap();

map.put("Key", "Value"); //To add an element 
String val = map.get("Key"); // To retrieve an element with key
map.renmove("Key"); // To remve an element with key

4. How does concurrentHashMap works internally?

Before Java 7,

the created map is segmented into smaller hashtables (16 segments). This is called segments. Each smaller hashtables has its own lock. So when write/read operation happen on a particular segment by a thread then that segment only is locked. This is called segment based locking.

For the read, We do not require locking unless there is a write operation happening on the same segment.

in Java 8,

Segments were removed.

So It would be like below.

map.put("test", "val");

It will first caluclate the hash for test and find the index with bit operation

"test" -> hashcode("test") -> 234234
234234 | (arraySize -1) -> 3

It is identified the index as 3 so basically third bucket it needs to be added. The thread who got this work will say, Hey if the bucket is empty insert this node. This is CAS why, it first compartes whether the bucket is null or not then insert it. Compare and Set (CAS).

If another thread already inserts then CAS fails. Thread retries operation and this is called CAS retry. Suppose bucket already has entries.

Now we need somekinda synchronization to do this. so bucket-level synchronization locking happens hence that particular bucket will be locked and not entire map.

That’s why,

ConcurrentHashMap is partially lock-free and not completely lock free.

In ConcurrentHashMap reads are mostly lock-free since it uses volatile visibility gurantees.

Java 8, ConcurrentHashMap combines, CAS, volatile reads, fine-grained synchrnoized locking and cooperative resizing to acheive high concurrency and scalability.

5. why immutable objects are easier for concurrency?

Most concurrency problems happen because multiple threads modify the shared mutable resources.

Immutable objects means their state is not going change after they have been created. Since the data never changes, threads can not interfere with each other, So no synchronization, no race condition, and no visibility problems.

6. Why can Double-Checked Locking break without volatile?

class Singleton {
   private static Singleton instance;
   
   public static Singleton getInstance(){
      if (instance == null { //First Check
        synchronized(Singleton.class) { // Class level Synchronization
           if (instance == null) { //Second Check
               instance = new Singleton(); //Object creation
           }
        }
      } 
      return instance;
  }

Actualy issue is Object creation is not an atomic behaviour.

  1. Allocate Memory
  2. initialize object
  3. assign reference

JVM may reorder like,

  1. Allocate Memory
  2. assign reference
  3. initialize object.

In case, if another thread may see non-null but partially constructed object.

If we add volatile to the object variable, then visibility is guaranteed to other threads.

JMM guarantees write to volatile can not reorder before object initialization. So correct order is enforced.

7. Why is ThreadLocal dangerous with Thread Pools?

When we have threadlocal for a thread, so the variable will be in the thread side. In thread pool we reuse the same thread hence the previous work data or old thread local data still exists.

ThreadLocal <String> user = new ThreadLocal<>();
user.set("Siva");

Request finishes and next request use same thread now. old threadlocal data still exists.

So in that case, memory leaks data leakage between requests and security bugs might happen.

So if we use thread local in thread pool, then you need to clear the threadLocal once the thread completes it works

try {
   //Logic 
} finally {
   threadLocal.remove();
}
