Liskov’s Substitution Principle

Is this principle really hard to understand?

You should have whatever your father has and do whatever your father does; only then will you be considered a true son of your father. Just imagine, in that case, your father can be replaced by you without any issues because you can handle whatever things he handled.

This is what we called as Liskov’s substitution principle. It states that objects of a derived class (child class) should be able to replace objects of the base class(parent class) without affecting the correctness of the program.

In other words, if you have a base class and you create new classes that inherit from it, you should be able to use these new classes wherever you use the base class. This should work without causing errors, unexpected behaviour, or breaking the program’s functionality.

Basically, Liskovs substitution principle help us to apply polymorphism without worrying too much.

How does Liskov…… help to do a clean code?

Scenario
Imagine you’re building a system to manage different types of products. You have a base class Laptop and subclasses MacBook and EliteBook.

class Laptop {
    void getPrice() {
        System.out.println("Price is : 0");
    }
}

class MacBook extends Laptop{
    @Override
    void getPrice() {
        System.out.println("Price is : 1000");
    }
}

class EliteBook extends Laptop {
    @Override
    void getPrice() {
        System.out.println("Price is : 5000");
    }
}

Correctness and Reliability
the LSP ensures that you can replace a MacBook instance with an EliteBook instance without breaking the expected behaviour. This demonstrates the principle’s advantage of correctness and reliability.

Since we follow the LSP, we ensure Laptop class all the methods are implemented in both child classes hence changing the child class is not going to affect program correctness and reliability.

Clearer Abstractions
LSP enforces clear and consistent abstractions in our code. When we know that any subclass can be used in place of the base class, we can rely on the interface and behaviour provided by the base class. This makes our code more understandable and predictable, especially when working in teams or collaborating on large projects.

Pitfalls in LSP

Violation of Semantics
It’s possible to create subclasses that technically inherit from a base class but don’t adhere to the same semantics. This can lead to confusion and unexpected behaviour. For instance, a subclass might override a method in a way that alters its intended meaning, violating the contract of the base class

Overly Complex Hierarchy
 Striving to adhere to LSP might lead to overly complex class hierarchies. Trying to accommodate all possible derived class variations can make your codebase harder to understand and maintain. Balance is key: prioritize meaningful abstraction over excessive inheritance.

Brittle Design
Over-reliance on subclassing can lead to a design that’s sensitive to changes. When you introduce a new subclass, it might inadvertently affect other parts of the system, causing unexpected issues.

Overhead of Unused Behavior
Subclasses might inherit behaviour from the base class that they don’t need. This can lead to increased complexity and unnecessary dependencies in the subclasses.

Don’t Strictly follow the LSP

  1. LSP might encourage us to include methods in subclasses that we don’t immediately need. This can sometimes go against the YAGNI principle, which advices against adding functionality until it’s necessary.
  2. When trying to create a common interface for multiple subclasses, we might end up including methods that are only relevant to certain subclasses. This can violate the Interface Segregation Principle, which encourages smaller, focused interfaces.
  3. LSP might require introducing methods in derived classes to adhere to the base class’s contract, even if these methods could be seen as separate responsibilities. Balancing the Single Responsibility Principle with LSP can be a challenge.

In conclusion, the Liskov Substitution Principle (LSP) serves as a fundamental guideline for ensuring the integrity, extensibility, and reliability of object-oriented software systems. Just as a true son inherits and seamlessly carries forward his father’s legacy, LSP emphasizes that objects of a derived class should seamlessly inherit the attributes and behaviours of the base class. This principle promotes correctness, reliability, and modularity in software design.

It’s important not to follow LSP blindly. Careful consideration must be given to the YAGNI (You Ain’t Gonna Need It) principle, Striking a balance between adhering to LSP and adhering to other design principles, such as the Interface Segregation Principle and the Single Responsibility Principle, requires thoughtful decision-making.

the Liskov Substitution Principle offers a foundational framework for creating robust, adaptable, and effective software systems. By upholding the essence of inheritance while remaining cognizant of its potential complexities, We can harness the power of LSP to build software that is both dependable and maintainable over time.
