How Request flows in Spring Boot?

  1. Client sends request to our application
  2. Request is first passthrough all filters before it reaches the web container. These filters belongs to servelt API. These filters are act like gatekeepers.
  3. the request reaches dispatcher servler. This is a front controller which has all information regarding the actual application controllers to route the request to correct controller.
  4. Once the Dispatcher servlet identify the controller then the request will pass through the interceptors which is between dispatcher controller and application controllers.
  5. once the interceptors passed the request will reach to the controller.
  6. Controller process the request and sends the response back.
  7. Again response follows the same path like interceptors, dispatcher servlet and filters then eventually it reaches the client.

Spring Security Architecture Key Elements


When you add spring security 6 in your application, Spring security will automatically add chain of security filters to the filters position so every requests needs to goes through those filters.

This chain of security filters are called Spring security chain filter.

 Before the controller method is called, the request is passed through multiple security filters.


FormBased Authentication Spring Security 6

When user enters the username and password, it would comes to UsernamePasswordAuthenticationFilter 

Application needs to verify the credentials entered by the user must be matched with the real stored credentials.

Authentication mechanism ensures where the application going to store the credentials.

  • In memory
  • External Database
  • OAuth2
  • JWT

Since these authentication changes based on mechanism, Spring simply externalize this mechnism instead of putting the logic inside the filter.

Developers knows why it is? becoz → Decoupling…

So this authentication mechanim instead of handling by the filter, it delegates to someone else. that is AuthenticationProvider.

Spring provides different providers for specific type of authentication.

  • OneTimeTokenAuthenticationProvider
  • DaoAuthenticationProvider
  • RememberMeAuthenticationProvider

But,

Filter doesn’t call each provider to check the authentication logic. 

Instead of doing that heavy check, it delegates checking and figure it our the provider to AuthenticationManager interface. 

So,

Filters do not call AuthenticationProviders for the authentication mechanisms they simply call the AuthenticationManager.

The primarly implementation of AuthenticationManager is ProviderManager 


Acutally,

  1. Client sends login-request to application
  2. As we know, request will passes through the filters and one of the filter is UsernamePasswordAuthenticationFilter 
  3. This filter creates an AuthenticationObject and delegates to ProviderManager wihch is an implmentation of AuthenticationManager.
  4. This ProviderManger has a list of authenticationproviders. It will loop through all providers and figure it out the provider which one is able to handel the authentication mechanism. 
  5. For this default form-based authentication, it would be DaoAuthenticationProvider.
  6. ProviderManager delegates the authentication mechanism work to the DaoAuthenticationProvider.


  1. DaoAuthenticationProvider fetches the user details from memory and compared the username and password which comes with AuthenticationObject.
  2. If password matches authentication would be successful otherwise authentication would be failed.

Once this authentication flow is completed, Spring security creates SecurityContext, Inside this SecurityContext authenticated user details are stored. 

For form- based authentication it would be username and password.

This SecurityContext would be preserved for the future requests. Upcoming requests of same user would be authenticated via SessionBasedAuthentication.

When the login is successed, the success response is sent to client. 

In this success response, SpringSecurity fetches the JSessionId from the HTTPSession which is created by tomcat container and attach the JSessionId in the responseHeader of the response.

So subsequent requests will be authenticated through SessionBasedAuthentication. 


SessionBasedAuthentication in Spring Security 6 

  1. Does Spring Security creates the session directly?
    NO

Spring security does not directly create sessions. Session is actually created by the servlet container. 

Once the form based authentication happened successfully, the response would send it with the JsessionId as I said earlier.

so subsequent requests, browser will inject the sessionId in the request header and send it to server.

So SpringSecurity reads the JsessionId and fetch the session then it matches the securitycontext with sessionId.


Default Spring Security Authentication Flow

application.properties

spring.security.user.name=sivaram
spring.security.user.password=abc@123

build.gradle

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-security'
    implementation 'org.springframework.boot:spring-boot-starter-webmvc'
    testRuntimeOnly 'org.junit.platform:junit-platform-launcher'
}

HealthCheckController

@RestController
public class HealthCheckController {

    @GetMapping("/healthcheck")
    public ResponseEntity<String> health() {
        return ResponseEntity.ok("SUCCESS");
    }
}

Now If I try to access the /healthcheck endpoint, it would redirect to login page.

Please note that /login, /logout endpoints are come from spring security not custom coded.

I will add password and username to login. sends the request to server.

Server sends us response and in the response header it sends us the JSessionId for the session.

JSessionId — E3E40A4CDA99B345B3D1A711F634E96F


So browser will use this sessionId to authenticate subsequent requests.


The default Spring Security provides form based authentication to authenticate the user and creates the session then the subsequent requests fo the user is authenticated through the session based authentication.
