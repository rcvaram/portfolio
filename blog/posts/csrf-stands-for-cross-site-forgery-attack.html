CSRF stands for cross site forgery attack.

Just think you visit your bank and also you visit the freewifi website. This freewifi website actually malicious website.

This FreeWifi website somehow it pretends like you and send a request to Bank API. It steal some information to pretend to act like you for example it is able to get your JSessionId and if it uses to pretend like you to the server by providing the JSessionId. 

This is called CSRF attack. 

The malicious website/attacker pretends like the victim or ligitimate client and use their information to get the access in the authorized websites through internal calls

JSessionId

When we login to the server. server provides a JSessionId in the response. This JSessionId will be used by browser to send subsequent requests to use the same session for the user. 

This JSessionId is the one used to authenticate the user in subsequent requests instead of asking password and username again and again.

If FreeWifi is able to get your JSesionId od your bank application, then it can also call their bank API.

If BankAPI only uses JSessionId to validate the authentication then BankAPI treats it is legitimate request and process it. 

If the request contains a transfer of all your money then that tranfer would work without you knowing it. 

How can freeWifi hold your JSessionId?


A web browser stores JSessionId in the cookie and automatically pass it in every API call to that application. that is how browser behaves. 


Lets illustarte it. I created a freewifi which internally calls the our bankapi health endpoint.

If you see the freewifi, you dont see any suspicious things right… but if you click, then it will send the form and this form call the bank api healthcheck endpoint.


When you click submit the form itself called the bankAPI healthcheck endpoint.

Let see what is happening when I click the freewif submit button.


It was sent the request to our bank API healthcheck endpoint. event it was directly sent by you. 

Browser automatically put JsessionId in the cookie and sends the request to the bank API healthcheck endpoint.

Now our spring boot server is under CSRF attack. because server thought it was sent by client but actually happened.

Even We added Spring Security Why It doesn’t protect the CSRF attack?

For the first lets understand which endpoint we called

We called a GET endpoint so in that case, the response still comes to your side and it was not sent to the freewifi. 

FreeWifi can not actually get the response. Browser automatically sends the JSessionId and different website is able to access the bank API but the response we get from the bank API is not acessible by the freewifi.

So Actually we do not need any CSRF protection for GET API. since the response is not going to access by the malicious website and also, GET API is not going to do any state change in the server.

Even browser automatically sends the JSessionId cookie, still the server rejects the request with 403.

How did this happened even Browser automatically injects JSessionId?

So there is something server validates addition to this JSessionId for state change APIs such as POST, PUT, DELETE and PATCH.

That is called CSRF Token. 

What is CSRF Token?

It is a unique value that has to be sent in Request Headers, in addition to the sessionId. 

It is to be sent all state changing APIs(PUT, POST, DELETE and PATCH).

It is not saved in cookies or sent automatically by browser in every API request.

We understood what prevents the CSRF attack. How the prevention is done using CSRF token?

How does the CSRF token prevent the CSRF attack?

There are multiple ways. 

  1. Server can expose an API to get CSRF token for clients to fetch the CSRF token.
  2. It could be rendered in some HTML form.
  3. Some Javascript code.

Create a CSRF endpoint manually to fetch the token



If you see here, we manually set up an endpoint to get this token.

We did not do any complex logic here. CSRFToken would be there for every request which passes through the CSRF protection filter.

In that case, /csrf-token also would have the token when it reaches the controller so we just extract the token from the request which is ultimately created by the spring-security and send it to client seperately.

I dont want to go depth how it has been created inside the spring security echo system but I will give a small conceptual idea.

  1. Request comes from client /csrf-token
  2. Whatever request is The request should passes through the CSRF protection filter which is from the spring security filter chain.
  3. CSRFFilter takes the request and delegate the CSRF functionality to CSRF mechanism /infrastructrue which is in the Spring Security.
  4. The default mechanim in Spring Securtiy is first it checks the method if it is POST/PUT/DELETE then it will validate request whether it has valid CSRFToken otherwise it would say request is forbidden that’s why we got it as 403 when we tried through malicious website and postman.
    If the request has valid CSRF token then it passes to dispatcher servelt and remaining process. 
    If the request is GET then its normally deos not do any validation. It will check whether we have an existing CSRFToken in the session if application has the token then it gives to filter or it creates and give back to the filter.
  5. Filter takes the CSRFToken from the Spring Security Infrastructure / Mechanism and add it to the request. 

That’s why we are able to get the token from the request attribute. 

Spring security 6 uses BREACH protection to alter the persisted CSRF token for each request. so basically same token used but the represenation of each request would change. so you will get different token presentation for each hit with this GET /endpoint.
Spring Security 6 CSRF token handling to include randomness on every request to protect against BREACH attacks.
