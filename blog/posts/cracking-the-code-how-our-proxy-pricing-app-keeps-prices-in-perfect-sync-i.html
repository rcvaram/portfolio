Cracking the Code: How Our Proxy Pricing App Keeps Prices in Perfect Sync — I

In the tech world, our pricing app is like a well-organized orchestra, thanks to something called microservices. Now, let’s dive into one…

The Massive Data Syncing Problem: System Design

We solved the real-world massive data syncing issue with micoservices making sure prices for our products are spot on!

Requirements for the pricing Application

👉 The producer should send 💰 price updates to the queue, ensuring the consumer receives them in the same order to display accurate prices 📈 for customers.

👉 It is possible to update the prices of multiple products simultaneously.

👉 Product prices are obtained from an external service. This service puts the price updates to us whenever the price is updated in the source system.

Tech Stack

Queue — AWS FIFO SQS

FIFO (First-In-First-Out) queues have all the capabilities of the standard queues, but are designed to enhance messaging between applications when the order of operations and events is critical, or where duplicates can’t be tolerated — From AWS Official Documentation

FIFO meets the requirements

  • First-In-First-Out Delivery → The sequence of sending and receiving messages is maintained strictly.
  • First-Exactly-Once Processing → A message is delivered once and remains available until a consumer processes and deletes it, ensuring that no duplicates are introduced into the queue

FIFO considerations

  • For FIFO queues, there is a maximum limit of 20,000 in-flight messages. In-flight messages refer to those messages that have been received from a queue by a consumer but have not yet been deleted from the queue. If you surpass this limit, Amazon SQS will not send any error messages. — Having a DLQ make sure we don't meet this due to incorrect messages.
  • A FIFO queue ensures that messages are processed in the order they are received. It does this by withholding the next message until the previous one is deleted. However, this means that the maximum throughput of a pure FIFO queue is limited — Message grouping by-product can increase the throughput

Language — Node with TypeScript

The requirement entails frequent I/O operations, such as reading prices and sending them to AWS SQS. While Java may be suitable for CPU-intensive tasks, concerns may arise due to its cold start runtime during frequent invocations. Python excels in scripting but falls short in terms of type safety, potentially leading to code maintenance issues. Although Go boasts strengths, its lower adoption compared to Node.js casts a shadow. Given Node.js’s high performance in I/O tasks, asynchronous programming capabilities, and increasing popularity in serverless environments, we confidently chose Node.js with TypeScript to ensure both type safety and code robustness.

Deployment with Serverless Framework

Selecting a serverless framework for deployment, as it is cloud-agnostic, ensures adaptability. In the future, if there’s a need to transition away from AWS, migration can be accomplished seamlessly

Architecture for the Producer Lambda function

External service put prices through ALB. ALB will trigger the lambda function. The pricing producer lambda function will create separate prices for products and put them into the queue. the consumer will listen to the prices and process.

REST API Design

POST Endpoint: /prices with below sample request body

{
   "products":[
      {
         "product_id":"1",
         "price":35.91
      },
      {
         "product_id":"2",
         "price":23.31
      },
      {
         "product_id":"3",
         "price":18.54
      }
   ],
   "created_at":"2024-01-01 12:04:12 IST"
}

This endpoint will be called by the external service to send the prices. Our producer lambda function will take this request and divide it into messages per product as below

{
   "product_id":"1",
   "price":35.91,
   "created_at":"2024-01-01 12:04:12 IST"
}

Then these messages will be tagged with group_id as product_id hence within the queue same product_id messages will only follow the strict orders and across the products, we can consume it parallel.
