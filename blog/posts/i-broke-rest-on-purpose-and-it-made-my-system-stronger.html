I Broke REST (On Purpose)—And It Made the System Stronger

REST is a beautiful idea. But real systems are messy, and REST is not enough to meet the Real Systems

I had an endpoint like below

DELETE /products/432

If I follow the REST here,

It should return 204 No Content Yeah, because you delete it and it’s done. No need to talk about it.

REST assumes Statelessness

In REST

  • Resources have URIS (e.g. /products/123)
  • Once deleted, the resource should not exist at that URI anymore

Therefore, if the user tries to get the product details again once he deleted it, with the below GET endpoint

GET /products/432

API should return 404 Not Found

Hmm..

But if the same product

  • Lived in invoices
  • Lived in customer orders
  • Kafka Data Streams
  • Lived in emails
  • Audit Logs

If I deleted it and returned 404 on future GETs, I’d be pretending it never existed. Seems like I am dishonest to the system’s truth.

So,

What I did

Instead of hard-deleting it, I soft-delete the product.

DELETE /products/432
200 OK
   {
     "message": "Product is moved to inactive status"
    }

And when someone tried to GET it again?

GET /products/432
→ 200 OK
  {
     "message": "This product is inactive"
  }

So now, my API

  • No breaking downstream systems.
  • No 404
  • Still traceable

The product hasn’t erased— I put it into the inactive state.

  • Invoices can still show their details
  • Historical reports don’t lose meaning
  • Streams don’t choke on missing references

But, Yes

REST says resources should disappear after deletion. In a distributed world, deletion isn’t that simple.

It’s not just about deleting something from a database. It’s about maintaining integrity, consistency, and traceability across many services.

Sometimes you do not wanna forget. You wanna a system to remember that something used to be there.
