Are You Still Using @Autowired Field Injection?

Field injection is not recommended

As of 2025, most Java developers are automatically warned by the IDE not to use this field injection when they try to do it in their code.

What’s Wrong with Field Injection?

Why is field injection not recommended?

  1. Testability is poor ❌
    Testing classes with field injection is tricky. You often need to use reflection hacks or Mockito @Mock and @InjectMocks to inject dependencies in tests.
  2. No Immutability ❌ 
    Fields injected this way are mutable and usually not declared final. That means your dependencies can change unexpectedly, leading to bugs.
  3. Hidden Dependencies ❌
    When we see the class constructor, we can’t tell what dependencies it needs. This makes the code harder to understand and maintain.

Constructor Injection Solves These Problems

With constructor injection, you tell your dependencies explicitly in the constructor

  • We removed the @Autowired annotation from the code.
  • We made the fields final.
  • We created the constructor with those final fields.

This Constructor injection is More AOT and GraalVM friendly.

Benefits?

  1. Clear Dependencies
  2. Immutability
  3. Better Testability
  4. More IDE and Framework Friendly

Don’t Worry About Boilerplate Code

Writing constructors for many dependencies can feel hard.

It could be avoided by using @RequiredArgsConstructor annotation of Lombok.

Declaring a field final signals to other developers: “This dependency is required and will never change.”

The beautiful thing is the least surprise, like no hidden mutations during runtime.

We can safely refactor without worrying about unexpected mutation in future.

Many dependencies in a class

Sorry to say this: You are a bad LLD designer. You should learn fundamentals

If you have multiple services injected into a service

  • High coupling — Tightly coupled to too many services
  • Difficult Unit Testing — Requires many mocks, even if only one service is needed
  • Hidden Responsibilities — Class might be doing too much (kind of a God object)
  • Long Constructor — Hard to read, hard to test, violates single responsibility

If you want, I can write a separate article on how to handle this situation.

In conclusion,

  1. Stop using @Autowired On fields, use constructor injection instead
  2. Utilize RequiredArgsConstructor of Lombok to not write boilerplate code.
  3. Check classes with too many dependencies. That usually means your design needs improvement
