Remote statement management

When working in a team, multiple people might be making changes to the same infrastructure. The remote state allows for proper locking mechanisms that prevent concurrent changes from causing conflicts.

Remote state ensures that all team members are working with the latest and most accurate information about the infrastructure’s current state. This reduces the risk of configuration drift.

Storing state files remotely reduces the chances of data loss or corruption. If a local state file is lost, it can be challenging or impossible to recover the exact state of your infrastructure.

Remote state solutions often provide version history, allowing you to track changes to the infrastructure over time. This can be invaluable for troubleshooting and auditing.

AWS S3 as a remote state backend

Using AWS S3 as a remote state backend for Terraform is a common and effective way to manage your Terraform state files. 

  1. Create an S3 Bucket → you’ll store your Terraform state files. Make sure to choose a globally unique name for the bucket
  2. IAM Permissions → Create an IAM policy that grants these permissions and attach it to the IAM user or role you’ll use for Terraform operations.

Once you create an S3 bucket, we can easily configure that in Terraform to store and retrieve the states. before that, To enable state locking for concurrency control, you need to create a DynamoDB table.

terraform {
  backend "s3" {
    bucket         = "ecs-fargate-states-bucket"
    key            = "path/to/your/statefile.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "ecs-fargate-states-dynamodb-lock-table"
  }
}
