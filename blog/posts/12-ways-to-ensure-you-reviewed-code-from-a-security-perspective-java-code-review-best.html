1. Validate All Inputs

Why it’s important: Unvalidated input is a primary cause of security vulnerabilities, including SQL injection and buffer overflows.

Bad Practice:

String query = "SELECT * FROM users WHERE id = " + userId; // Accepting input directly.

Good Practice:

int id = Integer.parseInt(userInput); // Check that input is a valid number.
PreparedStatement stmt = conn.prepareStatement("SELECT * FROM users WHERE id = ?");
stmt.setInt(1, id);
Always check that inputs are valid, and use prepared statements to avoid injection attacks.

2. Restrict Class and Member Access

Don’t let parts of your program that shouldn’t be accessed from outside remain public.

Bad Practice:

public String tpNo= "12345"; // Anyone can access and modify this.

Good Practice:

private final String tpNo= "12345"; // Now it's hidden and can't be changed.
Keep fields and methods private unless they absolutely need to be accessed from outside.

3. Use the Principle of Least Privilege

Give your app only the permissions it needs to function.

Bad Practice:

Runtime.getRuntime().exec("chmod 777 /important-folder"); // Full permissions given.

Good Practice:

Runtime.getRuntime().exec("chmod 444 /important-folder"); // Read-only access.
Avoid giving more privileges than necessary to reduce the risk of misuse.

4. Avoid Logging Sensitive Information

Sensitive data like passwords and tokens must not appear in logs.

Bad Practice:

logger.info("User logged in with password: " + password); // Logs password.

Good Practice:

logger.info("User login attempt at " + timestamp); // Only logs general information.
Log helpful details for debugging, but never sensitive information.

5. Handle Exceptions Securely

Don’t leak system details in error messages.

Bad Practice:

throw new IOException("File not found at /secure/folder/file.txt"); // Reveals file path.

Good Practice:

throw new IOException("Unable to access the requested file."); // Generic error message.
Be vague in error messages to avoid giving attackers hints about your system.
