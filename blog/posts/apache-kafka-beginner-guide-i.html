Apache Kafka Beginner Guide — I

Everyone knows how crucial is the starting point to add up a new piece to the head. If the new piece is Kafka then absolutely, you may confuse to start learning since there are so much information and ideas on the internet around Kafka.

I will be pretty sure that this blog will give you the fundamentals of Kafka And the point to start this Kafka journey together with me.

Let’s Start …….

First, before jump into Kafka, We need to know about the events which are published, processed, stored and exported via the Kafka platform.

Events / Messages​

Event is just a thing that has happened. Yeah Exactly, For example, “This blog is read” is an event and, another one is “Blog got some claps”. If you carefully look at these events, somehow Blog state is changed hence, these events can be referred to as state change as well.

You may get some idea about these events. There are a lot of events in this world. If we need those events, we define them otherwise we don’t care about them.

Once the event happens, that would never change hence, the event is immutable.

In Kafka, How are these events treated?
  • Events can be referred to in Kafka as messages as well (Just a naming convention).
  • A simple data structure and which is just a key-value pair.
{
    "key": "123",
    "value":"Blog clapped"
}

the value will be used to hold the event and the key is used to identify the place in Kafka, where it needs to be live.

  • Immutable, Once we write/publish the events in Kafka It will not be changed.

As Above,

Events are immutable and key-value pairs.

There are a lot of events so for simplicity or ease to access, we need to organise them. The topic concept in Kafka helps us to organise the events. It can be looked like a database table or a folder of the filesystem.

Topics are durables since it contains the immutable type events. These topics also have a retention period and, if that period expires events of the topic will be discarded from Kafka. In the first image, we have some blog post events, I just plan to organise them into a topic named Blog. This Topic concept is important since we can’t publish any events/messages without the topic.

Partitions

Imagine like we have several events for a topic and, the topic lives on a single node. Will this node handles the load? How can we distribute this kind of load to different nodes?

Kafka introduces partitions. Partitions do the tricks for us. The topic will be partitioned/split into partitions and, these partitions can be lived in different nodes. Kafka allows us to define the number of partitions when we create a new topic.
Additionally, we can increase the number of partitions dynamically but we could not reduce the partitions dynamically.

Obviously, we may have another question like how do these new messages identify which partition they need to go. This is the job of the message/event key. since I said the event is a key-value pair. This key is used to identify the partitions.

Messages in Kafka can be sent without keys and at that time, messages will be added evenly to the partitions.

Broker

The node/server of a Kafka cluster and is used to manage the partitions and handle the incoming/outgoing requests.

Overview of Kafka Setup

Here, Our Blog events are categorised into Blog topics with two partitions Partition 0 and Partition 1. These partitions live in different Kafka nodes Broker A and Broker B.

Now, we got some idea about how these messages are stored/organised in Kafka. but, how can we publish these messages into Kafka?

Producer API

Kafka provides producer API to produce/publish the messages on the topic. To send an event to Kafka we have to create a producer record that contains the event. A Sample Producer Record can be visualized as below.

In this producer record, We tell the event which is a key-value pair and the topic, partition in which we are going to produce the event. As I mentioned earlier, we can’t publish an event without a topic hence the topic is mandatory. After we are creating this producer record we can send it with producer API. And the producer API will do the rest up to send to the Kafka broker.

You can jump into consumer API if you are not curious to hear what’s happening inside this producer API.

  1. We(User Application) create a producer Record and give it to the producer API to publish the message into the Kafka cluster.
  2. Producer API’s Serializer module serialize the key and value (event) hence the event can be sent through the network as bytes.
  3. Producer API’s Partitioner module identifies the partition in where the particular producer record needs to be sent.
    a. If we specify the partition the data will be sent to that partition.
    b. If we don’t specify the partition but if we specify the key then based on the key, the partition will be picked by the partitioner. 
    c. If we don’t specify partition or key for an event then the partitioner will select the partition based on the round-robin mechanism.
  4. Now, producer API knows in which partition the data needs to be sent. So producer API will put this data into the relevant bucket/batch (Same topic and same partition).
  5. A separate thread is responsible to send this batch of data to Kafka. Once the response is received by the producer API. based on the response, producer API will do the remaining part like if we get retryable error it will retry otherwise it will notify the user Application.

Consumer API

Kafka provides Consumer API to consume the messages from Kafka. Consumers are usually part of a consumer group. Consumers can read messages across the partition​ parallel but in order within the partition.

When a consumer is assigned to partitions, It can read simultaneously across the partition which means, at the same time, Consumer Application can read Partition 0 and Partition 1 messages. But within the partition, It will read in order. In partition 0, the consumer Application will read the messages one by one.

How can we align these consumers to work synchronously? For that, we use consumer groups. When consumers are added to the consumer group. This Partition Assignment for consumers takes care by Kafka.

If we have one consumer in our consumer group, and our topic has 2 partitions then those two partitions are assigned to that consumer. So that, In Figure 1, Consumer I which belongs to consumer Group A consumes messages from both partitions.

If we have more than one consumer and less than or equal to the number of partitions then a subset of partitions will be assigned to each consumer. In Figure 2, we have 2 partitions and consumer group B has 2 consumers so that, consumer I can be assigned to Partition 0 and consumer II can be assigned to Partition 1. If we have 3 partitions then 2 partitions will be assigned to one consumer and one partition will be assigned to another consumer based on the strategy that we provided to Kafka.

If we have consumers more than the number of partitions then some of the consumers will be idle. It is illustrated in Figure 3.

When a new consumer is added or a consumer is removed from the consumer group. we have to reassign the partitions to the existing consumers.

Moving partition ownership from one consumer to another is called rebalance.

During rebalance, consumers can’t consume any messages since their ownership is revoked from the partitions.

So when the number of consumers of the group changes then the rebalance will be occurred. Rebalance is simply revoke partitions ownership of all consumers who belong to the same group and, then reassign some subset of partitions to all consumers of that group based on a certain strategy.

After rebalance occurs, how do consumers know in which place of the partition to start consuming. For this Kafka provide a mechanism to track the place using offset.

Unlike other data streaming platforms, Kafka offset tracking is a little different. Kafka allows consumer groups to track their place.

When a consumer group starts to consume messages from the Kafka topic, the Consumer group can commit the offset of each partition up to where it is processed. Then, when rebalance happens last committed offset of each partition will be known and it will be given to the consumers to seek from that position of the respective partition.

This offset management and rebalance mechanism are crucial things in Kafka Consumer API. I try to cover these topics in coming blogs.
