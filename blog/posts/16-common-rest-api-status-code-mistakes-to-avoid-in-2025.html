16 Common REST API Status Code Mistakes to Avoid in 2025

Did you know 70+% API bugs come from misused status codes?

I messed up this week. We’re building a REST API, and a user clicks “Generate Report.”

It’s a big task — takes a while — so I send back a 200 OK with a “Hold on, it’s coming!” message.

Done, right? Nope. My junior dev smirks and says, “Shouldn’t that be 202 Accepted since it’s still processing?”

Wait… what? I flip open RFC 7231, Section 6.3.3, and — yep — he’s got me! 😅.

That got me thinking: How many other status codes are we using wrong? Turns out, a lot.

1. Not Using 202 Accepted for Async Operations

❌ Bad Practice: Returning 200 OK for operations still processing.

Example: Report generation request.

POST /generate-report
HTTP/1.1 Response: HTTP/1.1 200 OK 
Content-Type: application/json {"message": "Report is being generated"}

1️⃣ User Requests Report Generation

  • The client sends a POST request to /reports generate a report.
  • The server does not generate the report immediately.
  • Instead, it starts a background job to process it and responds with 202 Accepted.
  • The response contains a Location header pointing to /reports/{reportId} where the client can check the status.

Request

POST /reports HTTP/1.1  
Content-Type: application/json

Response

POST /generate-report HTTP/1.1
Response: HTTP/1.1 202 Accepted
Location: /reports/12345
Content-Type: application/json {"status": "Processing", "estimated_completion": "30 seconds"}

2️⃣ User Polls the Report Status

  • The client checks the report’s status by sending a GET request to /reports/12345.
  • If the report is still processing, the server responds with 202 Accepted and status details.

Request

GET /reports/12345 HTTP/1.1

Response

HTTP/1.1 202 Accepted  
Content-Type: application/json  

{
    "status": "Processing",
    "progress": "70%",
    "message": "Still generating... almost done!"
}
✅ Best Practice: Use 202 Accepted for ongoing tasks/ asynchrnous response.

2. Using 200 OK for Failed Requests

❌ Bad Practice: Returning 200 OK for everything — even errors!

Example: Client requests /users/123, which doesn’t exist. Server returns:

HTTP/1.1 200 OK
{
    "status": "error",
    "message": "User not found"
}

Clients assume the request was successful, leading to confusion.

  • 400 Bad Request for invalid input.
  • 401 Unauthorized for no authentication.
  • 404 Not Found for resource not found.
✅ Best Practice: Use proper error codes

3. Misusing 302 Found for Redirects

❌ Bad Practice: Using 302 Found when redirecting after a POST request.

Example: After form submission, 302 Found causes the browser to resend the POST request, leading to duplicate submissions.

✅ Best Practice: Use 303 See Other to redirect after a POST request safely.

4. Using 404 Not Found for Incorrect HTTP Methods

❌ Bad Practice: Returning 404 when a wrong HTTP method is used.

Example: A DELETE request to /users/123 isn’t supported.

DELETE /users/123 HTTP/1.1 
Response: HTTP/1.1 404 Not Found 
Content-Type: application/json  {"error": "Resource not found"}
✅ Best Practice: Use 405 Method Not Allowed when an endpoint exists but does not support the requested method. Use 405 Method Not Allowed if the endpoint exists but the method is invalid. Use 404 Not Found if the resource itself does not exist.
DELETE /users/123 HTTP/1.1
Response: HTTP/1.1 405 Method Not Allowed Allow: GET, POST 
Content-Type: application/json {"error": "Method not supported"}

5. Using 500 Internal Server Error for Everything

❌ Bad Practice: Returning 500 for user input mistakes.

Example: Invalid parameters in a request.

GET /search?query= HTTP/1.1 
Response: HTTP/1.1 500 Internal Server Error 
Content-Type: application/json {"error": "Something went wrong"}
✅ Best Practice: Use 400 for malformed requests.
GET /search?query= HTTP/1.1 
Response: HTTP/1.1 400 Bad Request 
Content-Type: application/json {"error": "Query parameter is empty"}

6. Ignoring 429 Too Many Requests for Rate Limiting

❌ Bad Practice: Returning 500 when API is rate-limited.

Example: Too many requests from a client.

GET /data HTTP/1.1
Response: HTTP/1.1 500 Internal Server Error
Content-Type: application/json {"error": "Server error"}
✅ Best Practice: Use 429 Too Many Requests with Retry-After.
GET /data HTTP/1.1
Response: HTTP/1.1 429 Too Many Requests Retry-After: 60 
Content-Type: application/json {"error": "Too many requests, try again in 60 seconds"}

7. Not Using 422 Unprocessable Entity for Validation Errors

❌ Bad Practice: Returning 400 Bad Request for invalid data.

Example: Creating a user with an invalid email format gets a generic 400 error.

POST /users HTTP/1.1  
Content-Type: application/json  

{
  "name": "John Doe",
  "email": "test-email"
}

A 400 Bad Request means the server can’t understand the request due to malformed syntax. However, validation errors are not necessarily about malformed requests—they are about incorrect data that the server can understand but cannot process correctly.

HTTP/1.1 400 Bad Request  
Content-Type: application/json  

{"error": "Invalid email format"}
✅ Best Practice: Use 422 Unprocessable Entity for validation errors.

A 422 Unprocessable Entity means the request was well-formed (valid JSON, correct structure) but contains invalid data that fails validation.

HTTP/1.1 422 Unprocessable Entity  
Content-Type: application/json  

{"error": "Invalid email format"}

8. Not Using 304 Not Modified for Cached Responses

❌ Bad Practice: Sending full responses when data hasn’t changed.

Example: Ignoring If-Modified-Since header.

GET /profile HTTP/1.1 If-Modified-Since: Mon, 24 Feb 2025 10:00:00 GMT
Response: HTTP/1.1 200 OK
Content-Type: application/json {"name": "John"}
✅ Best Practice: Use 304 Not Modified with ETags.
GET /profile HTTP/1.1 If-Modified-Since: Mon, 24 Feb 2025 10:00:00 GMT
Response: HTTP/1.1 304 Not Modified ETag: "abc123"

9. Returning 200 OK for DELETE Requests

❌ Bad Practice: Returning 200 OK even if nothing was deleted.

Example: Deleting a resource.

DELETE /users/999 HTTP/1.1
Response: HTTP/1.1 200 OK
Content-Type: application/json {"message": "User deleted"}
✅ Best Practice: Use 204 No Content if the deletion was successful, or 404 Not Found if the resource does not exist.
  • If the user exists and is deleted successfully:
DELETE /users/123 HTTP/1.1  
Response:  
HTTP/1.1 204 No Content
  • If the user does not exist:
DELETE /users/999 HTTP/1.1  
Response:  
HTTP/1.1 404 Not Found  
Content-Type: application/json  
{"error": "User not found"}

10. Using 500 for Database Connection Issues

❌ Bad Practice: Returning 500 when the database is down.

Example: Database unavailable during a request.

GET /users HTTP/1.1
Response: HTTP/1.1 500 Internal Server Error
Content-Type: application/json {"error": "Server error"}
✅ Best Practice: Use 503 Service Unavailable.
GET /users HTTP/1.1
Response: HTTP/1.1 503 Service Unavailable Retry-After: 120
Content-Type: application/json {"error": "Database down, try again later"}

11. Using 201 Created Without a Location Header

❌ Bad Practice: Returning 201 Created without Location.

Example: New user created, no URL provided.

POST /users HTTP/1.1 
Content-Type: application/json {"name": "Jane"}

 
Response: HTTP/1.1 201 Created 
Content-Type: application/json {"id": 123}
✅ Best Practice: Include the Location header.
POST /users HTTP/1.1 
Content-Type: application/json {"name": "Jane"}

Response: HTTP/1.1 201 Created
Location: /users/123
Content-Type: application/json {"id": 123}

12. Returning 500 for API Deprecation

❌ Bad Practice: Returning 500 for deprecated API versions.

Example: Old API endpoint accessed.

GET /v1/users HTTP/1.1 
Response: HTTP/1.1 500 Internal Server Error
Content-Type: application/json {"error": "Server error"}
✅ Best Practice: Use 410 Gone for removed endpoints.
GET /v1/users HTTP/1.1
Response: HTTP/1.1 410 Gone
Content-Type: application/json {"error": "This API version is no longer supported"}

13. Using 403 Forbidden for Missing Authentication

❌ Bad Practice: Returning 403 when authentication is missing.

Example: Unauthenticated request.

GET /private-data HTTP/1.1
Response: HTTP/1.1 403 Forbidden
Content-Type: application/json {"error": "Access denied"}
✅ Best Practice: Use 401 Unauthorized for missing auth.
Thanks Mark Rigby-Jones for pointing out this in the comment section.
401 Unauthorized → When authentication is required but missing or invalid. [Basic, Bearer, or Digest authentication]
403 Forbidden → When authentication is present but insufficient for access.[session-based authentication, API keys, or custom authentication middleware]
GET /private-data HTTP/1.1
Response: HTTP/1.1 401 Unauthorized WWW-Authenticate: Bearer
Content-Type: application/json {"error": "Authentication required"}

14. Not Using 415 Unsupported Media Type

❌ Bad Practice: Not informing about unsupported content types.

Example: Request with a wrong content type.

POST /users HTTP/1.1
Content-Type: text/plain "John"

Response: HTTP/1.1 400 Bad Request
Content-Type: application/json {"error": "Bad request"}
✅ Best Practice: Use 415 Unsupported Media Type.
POST /users HTTP/1.1
Content-Type: text/plain "John"

Response: HTTP/1.1 415 Unsupported Media Type
Content-Type: application/json {"error": "Expected application/json"}

15. Handling CORS Issues Incorrectly

❌ Bad Practice: Returning 500 for CORS issues.

Example: Cross-origin request blocked.

GET /api/data HTTP/1.1 Origin: http://example.com

Response: HTTP/1.1 500 Internal Server Error
Content-Type: application/json {"error": "Server error"}
✅ Best Practice: Use 403 Forbidden for CORS blocks.
GET /api/data HTTP/1.1 Origin: http://example.com

Response: HTTP/1.1 403 Forbidden
Content-Type: application/json {"error": "CORS policy violation"}

16. Not Using 409 Conflict for Duplicate Resources

❌ Bad Practice: Returning 200 OK or 400 for duplicates.

Example: Creating a user with an existing username.

POST /users HTTP/1.1 
Content-Type: application/json {"username": "john"} 


Response: HTTP/1.1 400 Bad Request 
Content-Type: application/json {"error": "Bad request"}
✅ Best Practice: Use 409 Conflict for duplicates.
POST /users HTTP/1.1 Content-Type: application/json {"username": "john"} 

Response: HTTP/1.1 409 Conflict 
Content-Type: application/json {"error": "Username already exists"

Bad API status code practices can lead to confusion, security risks, and bad developer experiences. Avoiding these mistakes and using proper HTTP codes will make our API more predictable, scalable, and easier to debug.
