Transactions concept

A transaction is a unit of a program that manipulate/access various data items. Data persistent is the important thing in the software world. The database should be changed from one persistent state to another persistent state. After a successful transaction happens the database must be in a consistent state. During the transaction, the database may be in an inconsistent state. Often we refer successful transaction as transaction committed. 

Again, the data persistent is important, and in real-world, we mainly have two issues to maintain consistency of data.

  1. System failures → Including hardware failures, system crashes and etc.
  2. Multiple transactions can be executed in parallel (Concurrent execution of multiple transactions)

Example of a transaction

We have two accounts in the database Alice and bob and we need to transfer $1 from Alice’s account to Bob’s account.

For that, We need to do

  1. Get the balance of Alice account from the database (Read operation)
  2. Reduce $1 from Alice’s balance
  3. Update Alice’s balance in Alice’s account (Write operation)
  4. Get the account balance of Bob’s account (Read operation)
  5. Increase Bob’s balance by $1
  6. Update Bob’s balance of Bob’s account (Write operation)

Just a quick look at ACID properties


Atomicity 

Whenever we do a transaction, It should be atomic which means all the operations of the transaction are properly reflected in the database or none of them reflected on transactions. In our example, If our transaction is started then all 6 operations' result should be reflected or otherwise, none of them is reflected. 

Isolation

When we have multiple transactions and they concurrently are executed, their results should look like what if they run one by one.

If I have t1 and t2 transactions, they are concurrently executed. the thing is if I run first t1 and second t2 and get the change of the database or if I run t2 first and t1 second and get the change of the database, then this change/reflected the result of the database and concurrent execution of t1 and t2' change or reflected result on the database must be same.

It’s like t1 and t2 runs isolated environment and if we add up those two transaction results, then concurrent execution of t1, t2 transaction result must be same

Consistency

If we do transactions in isolation then the consistency of the database must be preserved.

Durability

After a transaction completes successfully, the changes it has made to the database persist, even if there are system failures.

Transaction states


Active → The initial state, the transaction stays in this state while it is executing

Partially committed → After the final statement has been executed transaction moves to this state.

Committed → After successful completion

Failed → When DB engine discover that normal execution can no longer proceed

Aborted → When the transaction is rollbacked and the database is restored to its previous state. 

Basically, when we start the transaction it will be in the active state, In this state, the transaction would fall to failed state if anything went wrong otherwise the transaction moves to partially committed state when all the transaction statements are executed.

Once the Database engine makes sure that everything happens well ( Stored properly) then transaction moves to the committed state otherwise It moves to failed state if anything happens wrong like couldn’t store the records.

Why do we need concurrent transaction execution?

  • Disk utilization can be improved

→ We can interleave the transactions when one transaction read other transaction can do other things

  • The average response time will be reduced

  → There is a possibility to finish short transactions without waiting for other long transactions.

How can we ensure the database is concurrently executed without violating ACID properties?

You Know, a transaction can be collections of queries and we may have a collection of transactions running at the same time. For that, someone needs to schedule those transactions.
