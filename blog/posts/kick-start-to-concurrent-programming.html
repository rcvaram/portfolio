Kick Start to Concurrent Programming

Concurrent computing is a form of computing in which several computations are executed concurrently — during overlapping time periods — instead of sequentially, with one completing before the next starts. from wikipedia

Problem in concurrent programming is we can’t prove the written code is correct or not unless we follow the some mathematical models. 

before we are going to start, we need to know some definitions in concurrent programming

Race condition

The situation where several processes try to access and manipulate shared data concurrently. As above we mentioned this Situation is called race condition.

We need to synchronize the processes to prevent race condition where this race condition occurs. This is the core objective of the concurrent programming.

To deal with this race condition, we have software level methods and hardware level methods. 

Critical Section Problem

Before going to address the problem, what is critical section?
 If we have n process and all competing to use some shared data. In here, Each process has a code segment called “Critical section” in which shared data is accessed.

“Actually, critical source depends on the problem not only the shared data”

Which means when there is a situation like race condition, the processes who makes race condition they have code segment in which shared data is accessed. we called this code segmentation as critical section.

The problem is we need to ensure that when one process in its critical section, no other process is allowed to execute in its critical section.

Mutual exclusion 

Two process will not collide, they will not run the critical section parallel. 
The formal definition is “ If process Pi is executing in its critical section, then no other process can be executing in their critical sections”
The reality is it is difficult to implement this mutual exclusion .

Progress

If no process is executing in its critical section and there exist some processes that wish to enter their critical section then the selection of the process that will enter to the critical section next can not be postponed indefinitely.
Which means always something should happens other than nothing.

Bounded Waiting

A bound must exist on the number of times that other processes are allowed to enter their critical sections after a process has made a request to enter its critical section and before that request is granted with the following assumptions

  • Each process executes at a nonzero speed
  • No assumption concerning relative speed of n processes

Concurrent programming is most of the time not fare to each process. Depends on the priority of the process, some process might get more than once execution before some other process are still not in allow to critical section. So if it is a bounded waiting, lowest priority process also can execute its critical section after some number of process passed to the critical section. This bounded waiting will remove the starvation problem. 


Critical Regions


  • t =T1, Process A enters the critical section before that also process A is running but not in the critical section. The request of the A is granted since there is no one in the critical section(Progress concept)
  • t=T2, process B tries to execute its critical section since process A is already in the critical section, process B can’t be allowed to critical section (Mutual exclusion concept).
  • t = T3, A leaves the critical section, so the critical section is now free so the process B can execute its critical section(progress concept ) This one is done by scheduler.
  • t = T4, Now all processes have done their critical sections.

Dead lock and starvation

Deadlock is two or more processes are waiting indefinitely for an event.

Assume that two critical resources S and Q , and two processes A and B where both process require both of the resources to proceed. Let’s assume A executes its critical section S and this sections needs critical section Q to execute otherwise critical section S will not finish. Same thing happens B as well like below B executes critical section Q and it needs where critical section S of Q to finish. Finally, A waits for Q resource with holding S resource and B waits for S resource with holding Q resource. 

This waiting can not be end. This is called Deadlock.

Starvation is indefinite blocking. A process is perpetually denied necessary resources to provide its work( Where you didn’t give fair amount to all process and you didn’t care about the bounded waiting)

Synchronization is used to prevent race conditions in concurrent programming.

Classical Problems of Synchronization

  • Bounded-Buffer problem(Producer-consumer problem) → There is a queue which is shared by two processes and one process tries to fill the queue and the other process is tries to empty the queue. We need some synchronization setup since if there is no item in the queue then the consumer should not process and same as if the queue is full then the producer should not process.
  • Readers and writers problem → The readers-writers problem relates to an object such as a file that is shared between multiple processes. Some of these processes are readers i.e. they only want to read the data from the object and some of the processes are writers i.e. they want to write into the object. The readers-writers problem is used to manage synchronization so that there are no problems with the object data. For example — If two readers access the object at the same time there is no problem. However if two writers or a reader and writer access the object at the same time, there may be problems.
  • Dining-Philosophers problem → K philosophers seated around a circular table with one chopstick between each pair of philosophers. There is one chopstick between each philosopher. A philosopher may eat if he can pickup the two chopsticks adjacent to him. One chopstick may be picked up by any one of its adjacent followers but not both. If you clearly understand this problem, we might end up with deadlock and possible for starvation.
When You tries to achieve mutual exclusion, You might end up with deadlock

Threads and processes

In order to define a thread formally, we must first understand the boundaries of where a thread operates.

A computer program becomes a process when it is loaded from some store into the computer’s memory and begins execution. A process can be executed by a processor or a set of processors. A process description in memory contains vital information such as the program counter which keeps track of the current position in the program (i.e. which instruction is currently being executed), registers, variable stores, file handles, signals, and so forth.

A thread is a sequence of such instructions within a program that can be executed independently of other code. The figure shows the concept:

Threads are within the same process address space, thus, much of the information present in the memory description of the process can be shared across threads.

Some information cannot be replicated, such as the stack (stack pointer to a different memory area per thread), registers and thread-specific data. This information suffices to allow threads to be scheduled independently of the program’s main thread and possibly one or more other threads within the program.

Explicit operating system support is required to run multithreaded programs. Fortunately, most modern operating systems support threads such as Linux (via NPTL), BSD variants, Mac OS X, Windows, Solaris, AIX, HP-UX, etc. Operating systems may use different mechanisms to implement multi-threading support.

In simple words,

Processes are like two people using two different computers, who use the network to share data when necessary. Threads are like two people using the same computer, who don’t have to share data explicitly but must carefully take turns.
