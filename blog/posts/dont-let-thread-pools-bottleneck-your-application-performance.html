Don’t Let Thread Pools Bottleneck Your Application Performance

Out of 100 concurrent user requests, if 20 have long-running database calls, only those 20 should face delays. But with traditional thread pools, up to 70 others might also be delayed. Curious how to fix this? Keep reading!

Read it from here, If you are not a medium member.

we analysed the impact of concurrency management on system performance by comparing two approaches for processing parallel tasks in a high-load environment.

The first approach used a traditional thread pool setup, while the second used structured concurrency with a Semaphore for concurrency control.

This article explains everything about the analysis and the results we got.

Sample Scenario

  1. A REST API can take item info requests from customers and execute them in a database Postgres function to get the results then format and send them back to the user.
  2. Due to some concerns, the function can take only 5 items in one DB call. however, customers can request 50 item detail requests from the request.
  3. I mocked this function with the following characteristics.
     — 90% (0–90%): A fast response to mimic typical cases (20ms to 150ms).
     — 9% (90–99%): Moderate delays (200ms–500ms) to reflect slower but acceptable cases.
     — 1% (99–100%): Severe delays (500ms to 20 seconds) to mimic edge cases or timeout scenarios.
  4. Jmeter script is created and it will make 7000+ requests in 900 ms.

Code

Postgres function

-- DROP FUNCTION IF EXISTS scs.get_item_info_func(text);

CREATE OR REPLACE FUNCTION scs.get_item_info_func(
    item_list text
)
RETURNS TABLE(
    item_no text,
    price numeric,
    quantity integer,
    description text,
    URL text,
    image text,
    cases integer,
    allocated numeric,
    stock_flag boolean,
    additional_info jsonb
)
LANGUAGE plpgsql
AS $function$
DECLARE
    delay_time double precision;
    random_value double precision;
BEGIN
    -- Generate a random value to decide the delay
    random_value := random();

    -- Determine the delay time based on the desired probabilities
    IF random_value < 0.9 THEN
        -- 90% of the time, delay between 100ms and 500ms
        delay_time := 0.1 + random() * 0.4; -- Random value between 0.1 and 0.5 seconds
    ELSIF random_value < 0.99 THEN
        -- 9% of the time, delay between 500ms and 2000ms
        delay_time := 0.5 + random() * 1.5; -- Random value between 0.5 and 2.0 seconds
    ELSE
        -- 1% of the time, delay between 1 second and 30 seconds
        delay_time := 1 + random() * 29; -- Random value between 1 and 30 seconds
    END IF;

    -- Introduce the delay
    PERFORM pg_sleep(delay_time);

    -- Return the query results
    RETURN QUERY 
    SELECT 
        '1234567' AS item_no,
        95.00 AS price,
        10 AS quantity,
        'Sample Item Description' AS description,
        'http://example.com/item/1234567' AS URL,
        'http://example.com/images/item_1234567.png' AS image,
        5 AS cases,
        50.00 AS allocated,
        TRUE AS stock_flag,
        '{"key1": "value1", "key2": "value2"}'::jsonb AS additional_info;

    -- Insert data into the ITEM_INFO table
    INSERT INTO ITEM_INFO (
        item_list, item_no, price, quantity, description, URL, image, cases, allocated, stock_flag, additional_info
    ) VALUES (
        item_list, '1234567', 95.00, 10, 'Sample Item Description', 
        'http://example.com/item/1234567', 'http://example.com/images/item_1234567.png', 
        5, 50.00, TRUE, '{"key1": "value1", "key2": "value2"}'::jsonb
    );
END;
$function$;

Java Code with Thread Pool Task Executor

The taskExecutor used here refers to a preconfigured traditional thread pool (e.g., ThreadPoolTaskExecutor in Spring or ExecutorService).

This ensures task execution is managed efficiently within the bounds of available threads.

Parallel Execution: Each productList is processed asynchronously using CompletableFuture.runAsync

// Execute product requests in parallel using a traditional thread pool setup
products.forEach(productList -> {
    CompletableFuture<Void> future = CompletableFuture.runAsync(() -> {

      }, taskExecutor).exceptionally(ex -> {

    });
    // Add future to the list
    futures.add(future);

// Wait for all tasks to complete
CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();

The Java code with Virtual Threads

// Use Semaphore to limit concurrent task executions
Semaphore semaphore = new Semaphore(1000);  // Maximum 1000 concurrent tasks

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    productInfoSubList.forEach(productList -> {
        // Fork a new task for each product list
        StructuredTaskScope.Subtask<Void> fork = scope.fork(() -> {
            semaphore.acquire();  // Acquire a permit before starting the task
            try {
                getProducts(productList);  // Process the product list
            } finally {
                semaphore.release();  // Release the permit after the task completes
            }
            return null;
        });
    });
    // Wait for all tasks to complete
    scope.join();
} catch (InterruptedException | ExecutionException e) {
    // Handle exceptions from structured concurrency tasks
}

Results

When we use Thread pool task executor

we observed the following behaviour:

From this data, it became clear that even lightweight requests (<100ms) were experiencing delays due to high-latency tasks (>2000ms).

Why this?

Thread pool reaches maximum threads it can create →
all threads are busy with high-latency tasks.
Lightweight tasks are queued and must wait for a thread to become available.
The thread pool is saturated now & new tasks are added to a queue →
contention occurs, causing additional delays or task rejections.

When we use Virtual Threads

The second approach, utilizing structured concurrency and Semaphore, has substantially improved the system’s handling of parallel tasks. Key improvements include:

  • Better Resource Management: Virtual threads allow threads waiting for I/O to be removed, freeing platform threads for other tasks to do instead of waiting.
  • Reduced Latency for Most Requests: With virtual threads, requests were processed faster as fewer threads were blocked on I/O. This significantly reduced the number of requests that experienced maximum waiting call times compared to the traditional approach.
  • Concurrency Control: The combination of virtual threads and Semaphore ensured tasks were executed within the system’s capacity, avoiding resource contention and enhancing overall efficiency.

Traditional Thread Pool Approach:

Handled tasks in parallel but struggled with resource contention. This caused high latency, longer database call times, and poor performance under heavy traffic.

Traditional Thread Pool Approach:

  • While it executed tasks in parallel, it suffered from resource contention, leading to significant latency spikes. Requests faced higher database call times, and the system struggled with load balancing under heavy traffic, causing suboptimal performance.

Structured Concurrency with Semaphore:

Limited concurrent tasks to avoid overloading resources.

  • Reduced latency and database delays.
  • Most requests were processed quickly (<1000ms), with fewer delays over 5000ms.
  • Improved load handling and resource efficiency.
This approach is ideal for high-load systems where managing latency and resources is critical.
The POC shows that structured concurrency outperforms traditional thread pools by improving throughput, and ensuring better system stability under load.
