Automating an Application Execution and Deployment with Terraform, Event Bridge Scheduler, Datadog, and GitHub Actions

In this article, I will discuss how to trigger an application for scheduled execution using the Event Bridge Scheduler. Additionally, I will explain how to export logs to Datadog within the Terraform task definition, create an entire setup using Terraform, set up GitHub Actions to automate the process and manage GitHub branches for deploying to various environments

This article explores a comprehensive approach to automating the execution and deployment of a Java application infrastructure. We will delve into the intricate workings of the Event Bridge Scheduler, leverage Terraform for infrastructure provisioning, integrate Datadog for streamlined log management, and harness the capabilities of GitHub Actions to orchestrate the entire process. Furthermore, we will guide you through the art of branch management on GitHub, ensuring seamless deployment across diverse environments. So, fasten your seatbelts as we embark on a journey to streamline and optimize your Java application deployment pipeline.

The architecture of this application

  1. The Java application deployed as a docker image. 
  2. The datadog API key is stored in the parameter store as a secure string
  3. The docker repository credentials are stored in the AWS secret manager.

We establish a task definition for an ECS task, where we retrieve the Docker image from the repository using credentials securely stored in the Secret Manager. Furthermore, we grant the essential permissions through task execution roles and task roles. To export logs to Datadog, we access the Datadog key from the Parameter Store, stored as a secure string. Following the creation of a task definition, the Event Bridge Scheduler facilitates the scheduling of tasks within an ECS cluster systematically.


Terraform Setup

We adhere to best practices for modularizing Terraform files, which leads us to create distinct modules for various components, including the ECS cluster, ECS task execution role, ECS task role, ECS task, Event Bridge Scheduler, and Event Bridge Scheduler IAM role.

 ECS cluster Terraform module (modules/ecs_cluster)


main.tf

#To create a ECS cluster you need a VPC
resource "aws_ecs_cluster" "this" {
  capacity_providers = ["FARGATE"]
  name               = "${var.cluster_name}-${var.environment}-ecs-cluster"
  tags               = var.tags
  setting {
    name  = "containerInsights"
    value = "disabled"
  }
}

variables.tf

variable "cluster_name" {}
variable "environment" {}
variable "tags" {
  type = map(string)
}

outputs.tf

output "scheduler_cluster_arn" {
  value = aws_ecs_cluster.this.arn
}

We have established a straightforward cluster using the Fargate provider within our Virtual Private Cloud (VPC). While it is possible to customize additional parameters within the cluster, for the sake of simplicity, no further configurations were applied in this module. You can check this official page for more information.

To make this module adaptable for various use cases, we have parameterized the cluster name, environment, and tags. Consequently, when utilizing this module, it is necessary to provide these parameters to create the cluster.

Furthermore, upon successful execution of Terraform to create the cluster, this module yields the ARN (Amazon Resource Name) as an output, providing essential information about the newly created cluster.

This Terraform configuration file defines an AWS ECS (Elastic Container Service) task definition, which is used to specify how a Docker container should run within an ECS cluster. It also includes some supporting resources like AWS SSM parameters and AWS CloudWatch log groups.

AWS SSM Parameters

  1. The first block retrieves a parameter named “DATADOG_API_KEY” from AWS SSM (Systems Manager) Parameter Store using the aws_ssm_parameter data source. The retrieved value can be used later in the configuration.
  2. The second block creates an AWS SSM parameter called “docker_image_parameter.” It stores the Docker image URL for the service specified in the var.service_name. The description provides information about the purpose of this parameter.

AWS ECS Task Definition

 A task definition is a blueprint for running Docker containers within ECS.

  • family: The name of the task family, which is composed of the service name and environment.
  • network_mode: Specifies the network mode for the task. In this case, it's set to "awsvpc," which is commonly used for AWS Fargate tasks.
  • requires_compatibilities: Specifies that this task is compatible with Fargate, a serverless compute engine for containers.
  • tags: Tags to associate with the task definition.
  • execution_role_arn: The Amazon Resource Name (ARN) of the IAM role that allows ECS to spin up the task. It typically needs permissions to access resources like ECR (Elastic Container Registry).
  • task_role_arn: The IAM role that the task itself will assume while running. It controls the permissions the task has to interact with AWS services.
  • cpu and memory: Specifies the CPU and memory resources allocated to the task.
  • skip_destroy: Prevents Terraform from destroying this resource.
  • container_definitions: This is a JSON-encoded list of container definitions, each describing a Docker container to run as part of the task.

Since we have three containers, lets deep dive into the containers.

Container Definitions

The container_definitions block specifies the Docker containers to run as part of the task. It contains an array of container definitions. For each container, it defines properties like the container name, Docker image, essential flag (whether the container is essential for the task), port mappings, environment variables, and log configuration. The first container definition corresponds to the main application container. It also configures log forwarding to Datadog using the AWS FireLens log driver. The second container definition, named “log_router,” is used for log routing and uses the AWS Fluent Bit image. The third container definition is for the Datadog agent, responsible for monitoring and tracing. It also configures log forwarding to AWS CloudWatch Logs.

AWS CloudWatch Log Groups

Two AWS CloudWatch log groups are defined. One is associated with the ECS task definition, and the other is associated with the Datadog agent.

This Terraform configuration allows you to define and customize AWS ECS task definitions using variables. We can provide values for the variables to tailor the ECS task for different environments and services.

Outputs are defined to provide easy access to critical information, such as the ARN and revision of the ECS task definition, after applying the Terraform configuration. These outputs can be useful for linking ECS tasks to other AWS resources, monitoring, or documentation purposes.

Event Bridge Scheduler (modules/event_bridge_scheduler)

main.tf

resource "aws_scheduler_schedule" "this" {
  name       = "${var.service_name}-${var.environment}"
  group_name = "default"

  flexible_time_window {
    mode = "OFF"
  }

  schedule_expression = var.scheduler_expression

  target {
    arn      = var.cluster_arn
    role_arn = var.scheduler_iam_role_arn

    ecs_parameters {
      task_definition_arn = trimsuffix(var.task_definition_arn, ":${var.task_definition_revision}")
      launch_type         = "FARGATE"

      network_configuration {
        assign_public_ip = false
        subnets          = var.subnet_ids
        security_groups  = var.security_groups
      }

    }

    retry_policy {
      maximum_event_age_in_seconds = 300
      maximum_retry_attempts       = 5
    }
  }
}

This Terraform creates a scheduled event using the AWS EventBridge Scheduler. It defines a schedule with a specific name, timing flexibility, and schedule expression. The schedule targets an AWS Fargate cluster specified by an ARN and uses an IAM role for execution. It also specifies networking configuration, retry policies, and other parameters for the scheduled task. The code employs variables to customize various aspects of the schedule, making it adaptable for different scenarios.
