1. What is a process & What is a thread?

A process is an independent execution environment.

It should have its own

  • Memory Space
  • Resources
  • File handles

A thread is the smallest unit of execution inside a process. Threads share the process resources such as

  • Heap memory
  • Opened Files
  • Database Connections
  • Application Context

However, each thread has its own

  • Stack Memory
  • Program Counter
  • Execution state

2. Why is thread considered as “lighter”?

You can see, If the OS needs to create process it needs to allocate separate memory space, resource table, process meta data and security context. but creating thread is cheaper because threads resue the same process resources.

Also,

  • Context switching between threads is faster
  • Communication between threads is easier as they use shared memory.
  • Threads consume less memory.

3. Can a thread exists without a process?

No…

A thread always belongs to process. For ex: in Java, The JVM itself runs as a process and, all java threads exist inside that JVM process.

When the process terminates: All threads inside it all are destroyed automatically.

What we can think is, Process is kind of Office and threads are Employess inside the office.

A thread is a lightweight unit of execution within a process. Since it shares process resources instead of owning them independently, It acts as lighter.

Right now, you understood all threads share the same heap. This is the main reason synchronization is needed to avoid race conditions. Race conditions happens when multiple threads access shared memory concurrently.

4. in Spring boot, If multiple users hit the same REST endpoint concurrently, how are the requests handled internally?

When multiple users hit the same REST API simultaneously are served by multiple threads not a single thread.

In Spring boot Application, For each incoming HTTP request is usually assigned a worker thread from server’s thread pool.

For example, if 50 users call the same API at the same time, tomcat can allocate different threads to handle those requests concurrently.

However there is a limit. Tomcat does not create unlimited thereads. It uses a configurable threadpool. it can be tweaked with application properties

server:
  tomcat:
    threads:
      max: 100

This means only 100 requests can actively execute at the same time. Additional requests will wait in a queue until a thread becomes available.

5. How can someone create a thread in Java?

  • Extending the Thread class.
  • Implementing the Runnable interface.
  • Using Lambda Expression(Modern Runnable)
  • Callable + Future
  • Using Threadpools(ExecutorService)
  • Using modern approaches like CompletableFuture
  • Extending the Thread Class
class MyThread extends Thread {

    @Override
    public void run() {
        System.out.println("I am running");
    }
}

public class Main {
    public static void main(String[] args) {
        MyThread t1 = new MyThread();
        t1.start();
    }
}

Actually run() method keeps the logic and start() method creates a new thread internally. If we call run() directly, no new thread is created.

The main limitation is this way extend the thread class restrict the class to extend any other class as Java does not support multiple inheritance.

This approach is good demonstrating purposes but its unlikely to use it in real world enterprise applications.

  • Implementing Runnable Interface (Preferred Basic Approach)
class MyJob implements Runnable {

    @Override
    public void run() {
        System.out.println("Job is executed");
    }
}

public class Main {
    public static void main(String[] args) {

        Thread t1 = new Thread(new MyJob());
        t1.start();
    }
}

This approach seperates the task logic from the thread management.

It ensures decouple the logic and thread management. Better design, It supports inheritance from other classes. It allows to reuse the task objects. It is most commonly used spring and enterprise systems.

  • Using Lambda Expression (Modern Runnable)
Thread t1 = new Thread(() -> {
    System.out.println("Running using lambda");
});

t1.start();

Because Runnable is a functional interface, lambda expressions make code cleaner.

  • Callable and Future
  1. Runnable can not return value.
  2. Throw checked exceptions.

Callable solve this.

import java.util.concurrent.*;

public class Main {

    public static void main(String[] args) throws Exception {

        Callable<Integer> task = () -> {
            return 0;
        };

        ExecutorService executor =
                Executors.newFixedThreadPool(5);

        Future<Integer> future = executor.submit(task);

        System.out.println(future.get());

        executor.shutdown();
    }
}
  • Executor-Service

Direct thread creation is expensive. Instead enterprise applications use thread pools.

ExecutorService executor =
        Executors.newFixedThreadPool(5);

executor.execute(() -> {
   System.out.println(Thread.currentThread().getName());
});

executor.shutdown();

Creating threads repeatedly is costly and, thread pool efficiently provide thread reusability, better performance, controlled concurrency and resource management.

  • CompletableFuture (Modern Asynchronous Programming)
CompletableFuture.supplyAsync(() -> {
    return "Hello";
}).thenAccept(System.out::println);

This is used in micro-services. This is non-blocking workflows, parallel API calls.

Actually, in real world enterprise, direct thread creation is uncommon. ExecutorService is standard and, CompletableFuture is increasing popular.

6. Can one runnable instance be used by multiple threads?

class MyTask implements Runnable {

    int counter = 0;

    @Override
    public void run() {

        int local = 10;

        counter++;

        System.out.println(
            Thread.currentThread().getName()
        );
    }
}

MyTask task = new MyTask();

Thread t1 = new Thread(task);
Thread t2 = new Thread(task);

t1.start();
t2.start();

A single Runnable instance can absolutely be used by multiple threads.

Here, t1, t2 threads share same task instance (Runnable Instance).

Each thread has its own stack while sharing the same object in heap memory.

When one Runnable instance is shared, we have scenario where multiple threads try to access shared mutable state.

Memory Breakdown

Heap Memory (Shared)

Object itself, Static variables,Instance variables are stored in Heap. Local variables and method calls are stored in Stack.

If you see the above code, counter varaible is in heap as it belongs to the object. So both threads can access the counter variable.

Since the counter variable is added in the logic, the both threads can update that variable without coordinatination and sometimes, some threads update might be reflected in the counter varaible value.

Example scenario

T1 and T2 read the counter variable at the same time and counter is 10 . both were run the logic hence both came up with 11 however it should be 12 as both threads counted. This is called Race Condition.

However the local variable will not be affected as it belongs to the thread’s stack.

If something is in heap (shared resource) and mutable then application needs synchronization.

Heap stores objects and instance variables which are shared among all threads. In Each thread’s private stack memory stores local varailbes and method call frames. So when multiple threads use the same runnable instance, they share the object state in the heap. This is why shared instance variables can cause race conditions while local varaibles are naturally thread-safe.

7. what happens if start() method is called twice on the same thread?

A thread can be started only once. If we again try to call the start() method on the same object then java throws IllegalStateException. Once a thread has completed its lifecycle, it can not be restarted.

In Java, A thread object is mapped to an OS-level thread. when we call start JVM creates native thread, OS resources allocated and execution starts.

After the thread finishes thread enters TERMINATED state. That same thread can not goback to NEW state So Java prevents restarting it.

Actaully start() method does much more than run method. It registers thread with JVM scheduler, it creates native OS thread, It allocates thread resources.

8. Can you explain thread cycle?

New state — JVM creates thread object but not started.

Thread t1 = new Thread();

Runnable state — JVM creates native thread and thread becomes eligible for execution. Runnable does not mean currently the thread is executing. It means the task is ready to run. and it is waiting for CPU scheduling.

t1.start();

Running State — CPU scheduler selects the thread. In this state, where the run() method is executing.

run();

Java combines Runnable and Running in Thread.State.Runnable however runnable is waiting for CPU, and running is actively executing.

Blocked State — When thread waits acquire a lock.

synchronized(lock){
}

If another thread already holds the lock then current thread blocked.

synchronized(obj) {
    Thread.sleep(10000);
}

Another thread trying same lock becomes blocked.

Waiting State — Thread waits indefinitely until another thread wakes it.

wait();
join();

TIMED_WAITING — threads wait for specific time.

Thread.sleep(10000);
wait(10000);
join(10000);

Terminated State — The thread finishes it works (complete it’s run method logic) or stops due to an error and thread can not be restarted.

In these states, Blocking, Wating, TIMED_WATING are can be treated as same.

9. If two threads are trying to update a counter varaible, what would happen and how to resolve it?

There is a possiblity of Race condition as this increment is not atomic.

Both threads may read the same old value of the counter, increase it and write it back. because this happens at the same time, one updatec an overwrite the other. So the counter value becomes wrong or inconsistent.

class MyTask implements Runnable {

    int counter = 0;

    @Override
    public void run() {

        int local = 10;

        counter++;

        System.out.println(
            Thread.currentThread().getName()
        );
    }
}

MyTask task = new MyTask();

Thread t1 = new Thread(task);
Thread t2 = new Thread(task);

t1.start();
t2.start();

If we do counter++, internally it is actually three steps.

  1. Read the current counter value
  2. Increment it
  3. Write it back it to counter variable

In case, if counter is 5 and t1 reads the counter value. meanwhile t1 increments and write it back, t2 also reads the same counter value 5. now t1 writes back to the counter as 6. since t2 also read the counter as 5 it will increment and write 6 as value to the counter variable.

Eventhough two increments happened, the final value becomes 6 instead of 7. This is called a lost update problem.

In real world, inder low traffic everything may look fine, once the traffic is increased and concurrent requests are increased, then these counts become inconsistent. These bugs are dangeours since they are intermittent.

Synchrnization hepls to solve this issue by only allow one thread to acess the shared resource at a time.

11. How will you solve this counter issue?

If correctness is more important than throughput, we can syunchrnize the crtical section aka the area where the shared resource is accessed by threads.

class MyTask implements Runnable {

    int counter = 0;

    @Override
    public void run() {

        int local = 10;

        increment();

        System.out.println(
            Thread.currentThread().getName()
        );
    }
  public synchronized void increment(){
       counter++;
  }
}

class Main {

MyTask task = new MyTask();

Thread t1 = new Thread(task);
Thread t2 = new Thread(task);

t1.start();
t2.start();
}

Since we synchronize the crtical section, only one thread is allowed to update the counter at a time. But the downside is contention.

Threads block each other and performace drops when the high concurrency happens.

Using Atomic Integer

class MyTask implements Runnable {

    AtomicInteger counter = new AtomicInteger(0);

    @Override
    public void run() {

        int local = 10;

        counter.incrementAndGet();

}

class Main {

MyTask task = new MyTask();

t2.start();
}

AtomicInteger uses CAS (Compate and Set) internally. This CAS is a lock-free CPU-level atomic operation. This is more scalable than synchornized for simple counters.

Using LongAdder for heavy contention

When we do metric collections from our microservice, even this AtomicInteger can become bottlenech because all threads compete o nthe same memory location.

LongAdder reduces the contention by maintaining multiple internal counters and combining them when needed.

t2.start();
}

You can choose

  1. Synchronization — Simple & Strong consistency.
  2. AtomicInteger — Light Weight atomic operations

11. How can you tell if your application’s slowness is due to lock contention?

First thing, we should verify whether threads are actually doing jobs or just waiting for locks. becoz, when lock contention happens, threads will be in blocked state instead of doing tasks.

We might see below symptoms if lock contention happens.

  1. CPU usage is not very high but response time is high.
  2. Eventhough u increas thread counts, still through remains same
  3. Threadpool queues starts growing
  4. A few requests takes too much time under load.
  5. GC looks normal, database looks healthy but application is still slow.

When we look into thread dumps, we need to check whether multiple threads are in blocked state with same monitor/lock. Then this a clear contention hotspot.

Using Java Flight Recorder (JFR), we have direct visibility to contended monitors, blocked duration, stack traces and hotspot methods.

We can see events like Java Monitor Blocked, Java Monitor Wait and Thread Park.

Moreover,

When you increase threads in your application and your application throughput doesn’t scale reasonably then the threads spend most of their time waiting instead of executing. This is a classic contention signature.

CPU Bottleneck

Lock Contention

13. What is reeantrant lock?

It is a powerful locking mechanism that control access to critical section. The same thread can lock the same lock again and again without getting stuck. It can also unlock the same number of times.

With Reentrant Lock

  1. More control over locking and unlocking
  2. Ability to try to get a lock without waiting forever.
  3. Setting fairness so the threads get the lock in order.
  4. Waiting with time limits.
  5. Using multiple condition variables.

14. How reeantrantlock works?

We can use the lock() method to lock the critical section and use unlock() to release the lock once our work is done. We could also use tryLock(), It does not block forever. If the lock is already held by another thread, it immidiately returs false so the thread can do something elseinstead of waiting.

Synchronized is best for simple mutual exclusion and most of the cases, it is better to use the synchonized word. Synchronized means wait until lock is free.

ReentrantLock is best when we need advanced thread coordination and lock control. ReentrantLock means We need fulll control overe how locking behaves.

17. What is volatile in Java?

visibility of shared variables between threads. when you marked the variable with volatile, you say JVM to whenever a thread changes this variable, other threads must immidiately see the latest value.

18. Why do we need volatile?

Each thread may cache variables locally. without volatile, If some threads change the value of that varaible, since the value is cached inside the thread memory, thread will see the old value which makes inconsistency in the system.

When we added volatile in the variable declaration then we say threads to always read latest value from the shared memory.

volatile boolean hasStopped = true;

19. Why doesn’t volatile guarantee atomicity?

Atomicity means an operation happens in one single step. Many operations (count++) are actually multiple steps

  • read value → increase → write back

volatile only guarantees visibility not that these steps happen together. So two threads can still read the same value and update it at the same time, causing wrong results.

20. Can volatile fix race conditions?

No. It is not guarantee the atomicity hence it cant fix the race conditions.

21. Can you explain the executor framework?

Executor framewrok is an abstraction or high level multithreading framework to manage threads efficiently and safely in Java.

Instead of doing raw works such as

  • thread creation
  • thread execution
  • thread reuse
  • task scheduling
  • thread lifecycle

these works are carried by the executor framework and as developers our part is just define the business logic as task and submit to the executor framework.

Threads are expensive as they requires stack memory, OS scheduling, CPU context switching and JVM management. Also Creating too many threads can weak your performance. Instead of creating new threads repeatdly, we can reuse the existing threads and this is called thread pooling.

We submit tasks and executor decides which thread executes them.

ExecutorService executor = Executors.newFixedThreadPool(10);

executor.submit(() -> {
              System.out.println(Thread.currentThread().getName());
          });

We have created executor with 5 threads. Then we submit a task to print the thread name in the executor. Executor will decide the thread and run this task.

22. What is executor Saturation?

When tasks arrive faster than processing, then the task queue grows and the latency increases. For example, you have 5 threads in your executor and each task takes 1 second however you get 50 tps (task/second). then additional 45 tasks will be in the queue and it will grow fast. This is called queueing delay.

When we have few threads, we may under utilize the executor framework and tasks can be queued up fast.

Also, when we have too many threads, then context switching, memory pressure and CPU thrasing might happen.

As a developer we need to decide proper size for the threadpool based on task

23. What is CPU-bound and IO-bound tasks?

CPU bound tasks are the tasks are fully or most of the time compuation needed tasks such as encryption and image processing. In those tasks, it is better to keep the thread count near to CPU core count.

I/O bound tasks are tasks that has waiting time for input/output such as DB calls, REST calls, file reads. We can use more threads because threads spend time waiting.

24. What happens if the executor task queue is full?

If both the thread pool is busy and the task queue is full, the executor rejects new tasks. This usually throws a RejectedExecutionException or follows a rejectionPolicy (like running the task in the caller thread or discarding it)

ThreadPoolExecutor executor =new ThreadPoolExecutor(corePoolSize, maxPoolSize,
                                          keepAliveTime, unit, queue);

When a new task arrives, executor check whether 
active threads < core threads: 
then it will create a new thread and execute it with the thread.

If all core threads are busy basically above condition fails, then executor put the task into queue.

If you have defined the task queue size, and the number of tasks exceed the queue size then it will check whether 
active threads< maxPoolSize
It will create a new thread and execute the tasks to ensure the tasks are not rejected.

If this condition (active threads < maxPoolSize )fails then it means queue size also full and executor creates it maximum threads so in that case, tasks get rejected. and this is the critical point.

This rejection is handled by RejectedExecutionHandler AKA rejection policy. DefaultPolicy is AbortPolicy which means throw an exception to fail the task immidiately.

This is very dengerours if it is not monitored. For example, You have sudden spike in your incoming REST requests, and async tasks get rejected then API failures and requests will be lost.

Instead of using AbortPolicy, we can ask the caller thread to run itself which slows incoming traffic naturally. It acts like backPressure. For this one you need to use the CallerRunsPolicy instead defualt one.

Instead of crashing, rejecting everything, system slows itself down gracefully. This is most common pattern in enterprise systems.

25. Why Queue Full is dengerous?

When queue is full means, tasks arrive faster than processing speed. This causes latency spikes, memory pressure and cascading failure. However large queue is not always good. Huge queue creates enormous latency, memory growth and slow failure detection.

26. What is completableFuture?

CompletableFuture is a java concurrency API used for asynchrnous and parallel task execution.

It allows us to execute tasks in the background and continue processing without blocking the main thread immediately.

CompletableFuture supports

  • Chainging — you can chain other asynchrnous tasks.
  • combine — You can combine multiple async tasks.
  • callback-style processing
  • Better exception handling

Think this scenario, when your REST API needs data from multiple services like customer service, prodcut info service, invoice service, order service, instead of calling them sequentially, you can call them concurrently using CompletableFuture to reduce overall latency.

CompletableFuture<Customer> customers = CompletableFuture.supplyAsync(() -> 
                                                            getCustomer());

CompletableFuture<Product> products = CompletableFuture.supplyAsync(() -> 
                                                             getProducts());

CompletableFuture.allOf(customers, products).join();

Here, both tasks are executed parallel, and we waint only after starting all requests.

Actually, CompletableFuture uses executor framework and threadpools underneath. ByDefault it uses the forkjoinpool but you can provide custom executor if you need.

If you see these CompletableFutures heavily used in

  • Parallel API aggregation
  • async notifications
  • background processing
  • report generation

The main advantage is improving responsiveness and reducing end-end latency.

27. How do we handle excpetions in CompletableFutures?

If an exception occurs inside a CompletableFuture, then that future is marked as completed exceptionally

The exception propagates through the future pipeline instead of throwing immediately to crash the main thread.

There are three common ways to handle the exception

  1. exceptionally
  2. handle
  3. whenComplete

exceptionally is most of the time used for fallback handling. Instead of failing the entire flow, we return a deafult value/fallback value.

CompletableFuture<Integer> future = CompletableFuture.supplyasync(()-> {
                                  throw new RuntimeException("Failure");}
                                  ).exceptionally(ex -> {return 0});

handle is more flexible as it receives both result and exception.

CompletableFuture<Integer> future = CompletableFuture.supplyasync(()-> {
                                  throw new RuntimeException("Failure");}
                                  ).handle((res,ex)-> {
                                  if (ex!=null) {
                                    return 0;}
                                   else {
                                     return res;}});

As we can see in the above code, this handle method actually centralize the success/failure transformation logic.

whenComplete is usually used for logging, monitoring or cleanup.

CompletableFuture<Integer> future = CompletableFuture.supplyasync(()-> {
                                  throw new RuntimeException("Failure");}
                                  ).whenComplete((res,ex)-> {
                                  if (ex!=null) {
                                    log.error("Exception occurred", ex);}
                                   else {
                                     return res;}});

If we finally call, join() method then Java could throws CompletionException which wraps the original exception.

Also, we use get() then checkedExcpetion might be thrown in program.\

If we don’t use get , join or exception handlers then failures may go unnoticed.

28. Can completeFuture cause thread starvation?

Thread starvation means task can not execute as all threads are occupied with tasks already. It usually happen because of blocking operations, small thread poolsm nested async calls and waiting on futures incorrectly.

ExecutorService executor = Executors.newFixedThreadPool(2);

CompletableFuture<Void> future = CompletableFuture.runAsync(() -> {
                                     CompletableFuture<String> inner =  CompletableFuture.supplyAsync(() -> {
                                                             return "hello";
                                                               }, executor);
                                     inner.join();
                                }, executor);

in case if we received two tasks simultenously and both tasks enter into the innerCompletableFuture but since we dont have more threads in the threadpool. two threads will wait forever. This is threadpool startvation.
